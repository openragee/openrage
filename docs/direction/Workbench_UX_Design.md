## Verdict

One application serves two people, and the design keeps them apart without keeping them in two modes.

- **The general modder** wants every file of a game and a project that holds whatever they are working on. They get a neutral Project screen, every workspace that exists, and nothing renamed.
- **The clothing creator** comes from a tool that is one screen and one Build button. They get a template that lands them on a Wardrobe screen with one thing to do, and they never meet the words project, module or output.

Four rules carry it.

1. **Without a project, the window is the same window.** The menu bar has the same six menus, and with no project the rows of Project wait, each saying why. The status bar is the one a project adds to, and the Project workspace and the task screens appear only while a project is open.
2. **The template decides what is seen.** It chooses the screen a project opens on, the workspace buttons that are shown and the words used. It is a starting point and never a type: any project can add any content later.
3. **The row of tabs is the only view switch, and it offers only views that have something to show.** There is no second selector. A project adds one neutral tab, Project, and one tab per kind of content that has a task screen, or one per content while it holds two of a kind; a file in front adds the ways to see it, while it has more than one.
4. **Nothing is written before Build, and every write is checked.** A build writes to a fresh folder, reloads what it wrote through the readers, and swaps it in, so a failed build never damages the last good one.

## Words

The screen says **Content** and **Builds**. The documents say module and output, which are the same things. The owner chose the screen words on 2026-10-07.

| Screen | Documents | What it is |
|---|---|---|
| Project | project | The folder and its `.openrage-proj` file; it has no type |
| Content | module | A kind of thing the project holds: Clothing, Map, Weapons, Particles, Addon ped, Files |
| Build | output | What the project produces: a FiveM resource, a singleplayer DLC, an installer |
| Template | template | A starting set of content, builds and a first screen |
| Workspace | workspace | A layout of panels; it has no scene of its own |

⚠ The Mods panel of today lists the installed mods of a game and their load order. It keeps its function and takes the title Installed mods, so that "mod" never means two things in one window.

## Flows

Each step says whether OpenRage already does it.

### Create a project

| Step | What happens | Today |
|---|---|---|
| Start | Start page, New project…, or File ▸ New project…, or the command palette | New |
| Template | A gallery with search and filters: Clothing pack, Map, Weapon pack, Particle pack, Addon ped, Empty project, Files project, Project from a folder. The right side says what the template contains and which screen it opens on | New |
| Details | Name, folder, game (Legacy, Enhanced or both) and the FiveM resource name, filled in from the name | New |
| Create | Writes the folder with its project file and a sources folder; the install stays mounted as the app's own mount | Exists |
| Land | Opens the template's screen with one next action in the middle, never an empty dock | New |

Only the templates whose content exists are offered. The Wardrobe has shipped, so the Clothing pack template and the Clothes card are there ([what the Wardrobe workspace builds](#what-the-wardrobe-workspace-builds)).

### Open a project

- **Four ways in:** File ▸ Open project…, the start page, dropping the project file or its folder on the window, and double-clicking it in the file manager through the file association. All four exist: a project file dropped on the window opens as a project wherever it lands (over a window with a project it asks where, as Open Project does), a dropped folder opens with the offer to open or make its project, and `.openrage-proj` is a file association that Settings ▸ File associations offers and suggests, registered for the person's account only when they press Register and taken back by Undo, which passes the path a launch opens as a project ([what the front door builds](#what-the-front-door-builds)).
- **Unsaved work** raises the question OpenRage already asks: save, discard or cancel. A project never replaces work silently.
- **Reading** is a job in the status bar. Keys the build does not know are carried through, and an older file migrates on its next save. Both exist.
- **Restoring** brings back the workspace, the tabs that were open and the one that was in front. It exists.
- **Checking** sends missing files and sources to the Problems list, each with Locate… and Remove, and raises no toast.

### Reopen a recent project

| Door | Today |
|---|---|
| Start page cards: name, path, what it holds, build state, opened how long ago | Five plain links |
| File ▸ Open recent, which lists the recent projects under a heading of their own with the command that clears them, and says why it is greyed while nothing has been opened | Exists |
| The project name in the status bar, which lists recent projects | New |
| Command palette: Open recent project | New |
| The launch itself, below | New |

A project whose folder moved shows Not found with Locate… and Remove from list, in place of the toast of today. Remove never deletes a file.

### Launch

The last project reopens by default, on the workspace it was left on, which is kept in the project's private folder and never in the file a repository shares (`the_workspace_a_project_was_left_on_is_kept_in_a_folder_that_ignores_itself`). The start page is one action away at any time: Project ▸ Close project, the View ▸ Start page command, and a Start page entry in the project menu of the status bar. A setting in Settings turns reopening off. With no remembered project, a launch opens the remembered install as it does today ([the_front_door.rs](../../src/state/the_front_door.rs) holds the cases that must keep passing).

### Switch view

- The screens of the project are tabs before the tabs of its files (`screens_as_tabs`), with no close button: Project comes first and is the neutral view, and task screens such as Wardrobe and Map follow, and exist only while the project holds that content; each is a row of the table of task screens (`src/ui/task_screens.rs`), which the tabs, Content, Open in, the start page and the palette read. Two contents of one kind are a tab each, named for the content (`screen_tabs`). While such a screen is on show no file's tab is. The strip draws the ways to see the file in front (`workspaces_in_the_strip`).
- A rail at the left edge has the rooms of the window, Home, Game, Project and Automate, with Help and Settings at its foot (`src/ui/panels/rail.rs`). A room brings its panel forward in the side column of the screen in front, Files, the Project panel or the log of commands, and the tab in front stays in front; the room of the panel in front is lit. Home is the start page, and with no project Project is New project….
- One panel, Details, is what is selected on the screen in front: a garment, a weapon, a placed thing of a map, an asset's properties on the Project screen, else the fields of the open file (`src/ui/panels/registry.rs`). A workspace of a kind of file (Browse, Model, Texture, Animation, Particle, Data) is a way to see a file and not a place to go: it is a button only while the file in front can be seen more than one way, a model as Model or Texture, particle effects as Particle or Texture, and it has none otherwise, since its button led to an editor with nothing in it.
- A bar under the tabs says where the thing of the tab in front is, and offers its primary command, filled, with at most three more (`context` in `src/ui/panels/document_tabs.rs`). Every kind of file has exactly one primary command (`primary_of`): Export to glTF… for a model, Replace from image… for textures, Go to file… for what is only looked through, Save for the rest. A screen of the project has no bar: the window's Build is the overview's primary action, and the commands of a content's screen, which the header of its list held, are at the right end of the row of tabs while it is in front.
- A right-click in the viewport offers Frame all, Frame selection and, for a model, Export to glTF… and Replace from glTF…. A right-click on the timeline plays or pauses, goes to the start and shows the whole length. The options of a clip's preview are behind a Preview options button at the viewport's top left and are no tab of the Animation workspace. A row of Files keeps Open, Import, Extract… and Export as… in its menu and opens the rest from Edit, Copy as and Compare. The key of Go to File puts the focus in the field of Files, and what the words name is listed under it with the scopes, the files opened lately, the arrows and Enter, until a file is chosen or Escape leaves; while the words only filter the tree, the list is a count that opens.
- Automate holds the command log, Batch…, the bake, and the plugins: the ones to run, the two commands that install one, and the Plugins panel, which holds what each was allowed and the settings each declared. Batch… runs Extract and Convert edition over the rows selected in Files, exports their models to glTF or their textures to PNG as one job, and gives the `openrage-cli bulk` line that extracts over a whole install.
- Clicking a Content row opens its default workspace as a suggestion. Right-click ▸ Open in ▸ gives any other. View ▸ Workspace and the palette reach every one, and Ctrl+1 to Ctrl+9 go to the tab in that place of the tab row.
- A template chooses which of the project's screens are tabs. The strip of the ways to see a file never wraps: what does not fit goes under More.
- The project remembers its workspace and its shown buttons.

### A second project

One project lives in one window. Opening another project from a window that has one offers Open in new window, which starts a second OpenRage process on that project. Two processes share the preferences file, so the first version writes it atomically and reads it again before a write; a real multi-window shell is a later decision.

### Open, Import and Add

Three words, each with one meaning, so that two buttons never do the same thing under two names.

| Word | What it does | Does it change the project? |
|---|---|---|
| Open | Looks at or edits a game file or an archive entry where it is, in a tab. Open Folder and Open Project are the same word for a folder and a project | No. Opening a file marks the project changed no more than opening it with no project open does; the project asks to save only for what a command put in it |
| Import | Decompiles a game file or an archive entry into a source in the open project: a `.ytd` becomes a `.textures.src` folder, a `.ydr` a `.drawable.src`, a `.ydd` a `.drawables.src`, a `.yft` a `.fragment.src` and a `.ymt`, `.ymap` or `.ytyp` a `.metadata.src`. A file with no source form yet (a text `.meta` among them), or whose source could not be made, is kept as it is under `files/`, in the Files content, and the report names the kinds it kept. The original is never changed | Yes, and it only adds |
| Add | Puts files into a project (Add files…) or into a pack (Add clothes…): a game file is decompiled at once, as Import does, and a source folder, an `asset.json` or a `.textures.src` comes in as it is. A file with no source form (a script, a text) joins the Files content | Yes, and it only adds |

The word Import means only the first. The five other things it used to name are called what they do:

| Was | Is | What it does |
|---|---|---|
| Import Texture… | Replace from image… | Puts an image's pixels over a texture of an open dictionary; Add texture from image… adds one as a new entry |
| Import glTF over this model… | Replace from glTF… | Reads a `.glb` or `.gltf` and replaces the open model's geometry, as one step to undo |
| Import File… | Copy into archive… | Copies a file from disk into a folder or an archive, which it joins when the archive is saved; the drop hint over an archive's folder says the same |
| Import n file(s), the undo of such a drop | Add n file(s) | The step Undo takes back |
| Import SWF, in the inspector of a `.gfx` | Replace from SWF | Replaces the open movie with an SWF saved from an editor, as one step to undo |

An opened folder is a place to look in and never a member of the project, so it adds no row and no problem to the Assets table. Reading a file is never Import: Open on a `.lua` of a resource opens it in the Data workspace's text editor, and nothing in the project changes.

Import is three commands and one window.

- **Import game files…** (Project menu and palette) picks several files, and **Import into project** (a file's menu in Files and in the centre, beside Open, and for several selected files) imports the rows chosen. A file inside an archive is read from the archive and keeps the path it has there, and the archive is not written. Selecting a whole archive or a folder inside one is refused with the way to do it: select the files in it. A folder on disk is walked, as `openrage-cli project import` walks it: each file in it with a source form becomes a source, and any other file is kept whole under `files/` and joins the Files content. An archive found in the walk is not kept: the report lists it as left out with the way in, which is to open it and import the files in it, since `files/` keeps a file whole and an archive is gigabytes. An archive picked in Import game files… or dropped is refused for the same reason, since neither can name the files in it. The build label a source states is the install that holds the file, never the one that happens to be mounted.
- **Import folder…** (Project menu and palette) picks one folder and walks it, as dropping it on the Project workspace does. The walk reads 8 levels of folders and 10 000 files at most, and the report says so in a line of its own whenever a folder was walked, then lists what the bounds left out.
- **Add images as a textures source…** puts the images picked in one new `.textures.src` that says it was authored, with no DDS until it compiles.
- With no project open each is disabled with *Open or create a project first*, and pressing it with the key says so in a toast that offers New project…. A second import waits for the first.
- The import is a job of the status bar, off the UI thread, that counts: once the walk has found its files the job reads `3 of 40 files` and the name it is on, with a bar, and its Cancel stops it after the file in hand. What it had made stays, each source whole, and the report says it stopped, lists the files it did not reach and keeps Undo import for what was made; importing the folder again finishes it, for a file already a source is skipped. Each source it makes joins the cook that already watches the project, so its row appears in Assets with no refresh and opens in the workspace of its kind: a textures source in Texture, a drawable in Model. A source's Properties say where it came from and the file it compiles to, a `.ydr` for a drawable source and a `.ydd` for a drawables source.
- The import ends with one message, and which one depends on whether anything needs reading. An import that worked ends with a toast that says what was done in a line, with no count that is nought (*Imported 3 files: 2 became sources, 1 was already a source*), and has **Undo import**, which takes the import back, and **Show report**; once another import has ended after it, the button of the older toast takes nothing back and says so (`an_import_says_what_it_did_in_a_toast_and_its_button_takes_it_back`, `an_import_that_made_nothing_offers_no_undo_and_the_toast_of_an_older_import_takes_nothing_back`, `an_import_that_worked_is_a_toast_with_two_buttons_and_opens_no_window`). An import with something to read, a file refused or kept as it is, a file or folder left out, a stopped walk, opens the report window and raises no toast, since the window has Undo import itself (`an_import_with_something_to_read_opens_a_window_of_plain_sentences_below_the_table_and_raises_no_toast`). The window sits at the foot of the screen, so the table the import filled stays in view above it. It lists each file with Made, Already a source, Kept as it is (added to the Files content) or Refused and what happened in a plain sentence, the library's own words with the hex and the hashes in the hover and in the Log, then a line naming the bounds of the walk when a folder was walked, and the files and folders a bound left out or an archive in it. A stopped import says so and lists the files it did not reach. Show in Assets selects the first source made. **Undo import** removes exactly the folders the import created and nothing is removed if the digest of any of them changed since; the project's History keeps one line for the import and one for its undo.
- **Drops.** What a drop from the file manager does follows the screen under the pointer, and the hint that follows the pointer while the drag is held says which: on the Project workspace the hint reads *Import into the project* and the drop is Import (the same walk as Import folder…); on the Wardrobe it reads *Add as clothes*; on a folder row of Files it reads *Copy into archive* or *Copy into folder* and the name of the folder, with *Copied at once* under it for a folder on disk, *Added now, and written when the archive is saved* for an archive, and *Read only: this drop will be refused* in a quiet plate, with no outline, where the edit mode would refuse it; anywhere else, Browse, Model and the rest, and over the start page, it reads *Open in OpenRage*, with *Opens the file where it is. Nothing is changed* under it, and the drop only opens, as before. The hint is a plate beside the pointer, filled and outlined and kept inside the window, with one line under its title that says what the drop changes (*Decompiled into sources. The originals are not touched* over the Project workspace), so it reads over whatever is under it (`the_hint_of_a_held_drag_is_on_a_plate_inside_the_window_and_says_what_the_drop_changes`). A dropped folder opens as a folder, which offers *Make this a project* or, when it holds a project file, *Open project* (while no project is open, as for any opened folder), and a folder that holds a project, dropped while another project is open, asks whether that project opens here or in a new window, and is never imported into the project that is open; a dropped `.openrage-proj` opens as a project wherever it lands. A drop of models or texture dictionaries on a project that holds no clothing asks first: *Make clothing* gives the project a clothing pack and the dropped files become its garments, *Import as sources* imports them as any game file, and Cancel does neither. Only the files named in the drop are looked at, never the inside of a folder.
- **Import a built pack.** It is Import, since a pack is a game file that becomes sources in a new folder and is never changed, and Open changes nothing. Import built pack… (File, a button of the start page, and the palette; it needs no project) picks a `dlc.rpf`, an `.oiv` or a grzyClothTool `.gctproject`. A drop asks the same question: an `.oiv` or a `.gctproject` dropped anywhere but an archive's folder, and a `dlc.rpf`, the name every singleplayer DLC has, dropped on the Project workspace, where an archive cannot be imported whole; any other `.rpf` is not a pack of this kind and is dealt with as it was before, opened as an archive anywhere but the Project workspace and refused there with the way in. Several packs dropped together are asked about one after the other, and the hint under the pointer reads *Import as a project* over a pack that will ask, worked out from the names held alone, so that a held drag reads no folder (`a_built_pack_asks_to_be_reopened_where_a_drop_puts_files_in_the_project_and_an_rpf_elsewhere_still_opens`). The question is *Import dlc.rpf as a new project?*, with the file's name in the title: the file and what it is, one sentence at the size of the page that says every model and texture becomes a source in a new folder and that the pack and the person's other files are never changed, the project's name (Name; the button waits for one and says so), the folder it is made in (Create in, as New project says it; Browse… picks one, and it offers the folder the last project was made in) and the pack's name only once the reader has refused the one the pack states. A name that cannot be a folder, a folder that is not there and one that already holds something are said in the question and nothing starts; a pack the reader refuses brings the question back with the reason in one sentence at the size of the question, with the file's name and no path and no name of a library, and the reader's own words in its tooltip, in a row the question keeps whether or not it holds one so that the buttons stay where they were (`a_folder_for_the_project_must_be_a_name_in_a_folder_that_is_there_and_holds_nothing_of_that_name`, `a_pack_the_reader_refuses_brings_the_question_back_with_the_reason_and_makes_nothing`). The answer runs on a worker as the job *Importing dlc.rpf as a project*, in the status bar and the Jobs panel, with the count of files read and the one it is on, and Stop makes nothing: no folder is left behind and the pack is not touched (`a_stop_asked_for_makes_nothing_and_says_so_and_a_pack_waits_while_another_is_read`, `a_reopen_counts_the_files_it_reads_and_a_stop_asked_for_makes_nothing`). The report is a window, *Pack imported*: the garments and textures that became sources, the new folder, and the files that could not be placed, each with its reason and, for a file kept, the name it has under `files/` (the build writes `content.xml` and `setup2.xml` again, so they are named and not kept); Open project opens what it made, asking first, as every project does, whether it replaces the open one or opens in a new window, and Reveal in the file manager shows it (`a_dlc_dropped_on_the_project_workspace_asks_runs_and_reports_where_it_kept_what_it_could_not_place`). The result has no Undo, and the window says so: it is a new folder and the pack is never written, so deleting the folder takes it back. It reads files and says nothing about the game loading the pack.

### Close

Project ▸ Close project returns to the start page with the install still mounted. A build is atomic, so closing the project does not ask about a running one: it finishes, and what it wrote stands or the previous build does. Sources are saved as they are edited, so a project never has a save-all-or-lose-all moment; what the project file itself holds, such as a file added or a build declared, is written by a save, and a project that has such a change asks to save it before it closes, as a second project, a new session and exit do.

The screen for a clothing creator, opened by the Clothing pack template. - **Dropping files** adds every garment found, reads the ped and slot from the names, marks what it cannot read with a question mark, and says what it did in a toast with Undo. It never overwrites a source. A picture named as a texture is made into the texture of its variation, and a drop of thousands of files shows how far it has got and can be stopped.
- **A texture** is replaced by dropping an image on its variant, or by saving one beside the file from an image editor; the texture is recooked as it is saved and the preview updates. There is no convert button.
- **Slot and position** are filled in by the rules. A garment keeps an invisible stable id, so renaming or inserting breaks nothing that points at it, and a position that moves is flagged in the build diff.

### The Build tab

A header line says what the build would write in one sentence (`14 files, 2.8 KiB, 1 error stops this build`, or `nothing stops this build`) and, in a line of its own under it, the counts added, changed, moved and removed: what the next build would change when something was edited since the last (`Since the last build: …`), else what the last build changed from the one it replaced (`This build changed: …`), so that a build that removed a garment never says that nothing changed beside it; the line is not drawn for a build that has no earlier one or that changed nothing, since a line of noughts is noise (`what_a_build_changed_is_said_once_where_the_changes_are_and_never_as_nothing_beside_a_removal`). Above them, under the buttons, is the answer to whether it worked. After a build that went through it is one line: how many files were written and read back, whether a second build wrote the same bytes, and that loads in game is not tested. After one that stopped it is a red block beside the word Failed: the step it stopped at (`The build stopped at step 3, Write to a fresh folder.`), that the last good build is as it was, the first three reasons, each naming a file as the project does (`missing_hat.ydd is missing`, never a path of the disk or a backtick) and led by a bullet that is not the dot of a state, and a button, Show in Problems, which lists the rest. Under it are the five steps in a row (plan, cook what changed, write to a fresh folder, read every file back, swap it in), each behind the one running ticked, the one running marked with an arrow and a colour and the one a build stopped at with a cross, since a state that rests on a colour is lost. While a build runs the Build and Build all buttons are replaced by Cancel build, a bar and the file it is on show under the row, and Edit build… waits with its reason; once a build is there, Show the build shows its folder in the file manager, as the toast that ends the build does. Then four sections that fold, in the order of a build, with the plan and the size map folded and Verification open once a build has gone through. Plan: the files copied and cooked, the size and each figure against its limit, said in words and in the units of the size (`Clothing memory: 81.5 MiB`, never the engine's name for it or a count of single bytes), one line when no limit is set, the garments in each slot (`Tops: 3, Hats: 1`), the items that keep a stable id, the plan's problems, and a heading with the count of the files it writes, each by its own name first, then its size and what is done to it (copied, converted, built from source, written), then its folder in grey. What changed: added, changed, moved and removed, of the next build or of the last as the line above says, open when there is something in it, and a warning with an exportable redirect map when ids changed position; the same difference is never said a second time under Verification. Verification: what the last build wrote and read back, in sentences with no backtick, no `(s)` and no name of the engine's types (`the_check_of_a_build_is_in_sentences_with_no_markup_no_engine_type_and_no_file_of_the_tool`): where it was written (`build/tshirts`, the whole path on hover), every file read back and equal to the plan, the files opened again to check them and the kinds of file OpenRage cannot open, the metadata documents by what they are (clothing variation metadata; the engine's name for the type is the hover), what freezing did (`The places of the 16 garments of uniforms are locked, so a later build cannot move one unless a reason says why`, with the file that holds them on hover), the check of each clothing pack as a tick or a cross and a sentence and never ok or FAILED in letters, whether a name is held twice, the streaming memory against its ceiling, whether a second build wrote the same bytes, what was seen of its kinds of file in a running game, and the list of every file opened again, each with the kind it is (a texture dictionary, a drawable dictionary) and the reader in its hover, which scrolls and is never cut short. Size map: where the bytes of the resource are. The last line, loads in game, is never ticked by the tool: a tester records it per kind of build.

What a tester recorded is the acceptance sheet ([In_Game_Acceptance.md](../guides/In_Game_Acceptance.md)), and the Verification reads it for the resource a build wrote, in the edition the build was written for and in each of the two when it states none (`src/ui/panels/project/in_game.rs`). Where a line of the sheet about a kind of file the build wrote has no newest result of loaded, one sentence counts those kinds and names them as a person does (`2 kinds of file this build wrote were not seen loading in GTA V Legacy: maps, type files`), and a link under it, How to check it in the game, opens the acceptance guide at the steps that load a build of that kind, on a FiveM server or in story mode (`the_link_under_a_story_pack_opens_the_steps_for_story_mode`). The reading is of the build that is on the disk: stating another edition for the next build changes nothing of it until that build is made. Where every such line was last seen to load, the sentence says so with the day of the newest result, and there is no link. A build that wrote no kind a line is about gains nothing. The sentence says what was or was not seen and never that a file loads, and `openrage-cli project build` and `wardrobe build` print the same reading in the same English (`the_tab_and_the_command_say_a_reading_in_the_same_english`).

## What stays a disadvantage

No design removes every cost, so these are the ones that remain.

1. **More concepts than Durty Cloth Tool.** The template hides them from a beginner, but Project and Builds exist and appear as soon as the Project button is pressed.
2. **Two copies on disk,** the sources and the build. The exact DDS keeps sources compact and Clean empties the build.
3. **Nobody here can prove that a pack loads in game.** The last verification line stays unticked until a tester records it.
4. **A strip that can overflow.** It takes nine buttons when a project holds Clothing and Map, and More catches the rest on a narrow window.
5. **Two windows are two processes** in the first version, with a shared preferences file.

### Each drawback of the project approach, and what answers it

The owner named seven drawbacks of making clothes in a project instead of in the one screen of Durty Cloth Tool. Each has what answers it in the tree, and the five above are the costs that remain after the answers.

| Drawback | What answers it |
|---|---|
| More concepts | A template starts a clothing creator on the Wardrobe and hides Project and Builds until the Project button is pressed; the screen says Content and Builds, never module or output |
| Hidden source folders | Every `.src` folder is a row of the Assets table with its kind, size and state, Reveal asset shows it in the file manager, Properties says what it holds, and a source is plain files (a glTF, a DDS, JSON) that any other tool opens; the Wardrobe lists garments and not folders, so a clothing creator need not look in one |
| A cook that looks slow | A saved source is cooked again at once, alone, in the background: its row says it is not cooked until the cook ends, the job is in the status bar and Jobs with a Stop, and a scan counts only what changed since the last one |
| Missing features at launch | Every row of the feature matrix of the three tools is present, planned in a named wave or excluded by a recorded ruling in [Wardrobe_Parity.md](Wardrobe_Parity.md); a file with no editor still opens as a file, and the Files content ships what no kind of content owns as it is |
| Huge lists | The Assets table filters by kind, by problem and by name, the Wardrobe's query bar selects by terms and groups by ped and slot, every walk of folders is bounded and says when it stopped, and a pack with very many garments is scanned once and then by what changed |
| Onboarding | A sample project with one problem to find, a six-step tour, the guide under Help, a `?` on Problems and Build, and a tooltip on the Wardrobe's controls that names its guide section, which Shift+F1 over the control opens |
| Data loss | An import only adds, a replacement writes over no file, every change of the Wardrobe is a step of Undo and a write of the pack keeps a version, the project's History goes back to any step, a build never replaces the last good one, and Clean empties only what a build wrote |

- **The template and the goal.** The Weapon pack template declares the Weapons content and one FiveM resource named after the project, opens on the Weapons screen and pins Project, Model, Texture and Weapons. Its chip on the start page is the table's (Weapon pack).

## What project history builds

Wave P16 of [Workbench_Plan.md](Workbench_Plan.md) made every change to what a project holds a step that can be taken back, in `src/state/workbench/project_history.rs` for what moves along the steps, `crates/domain/or-project/src/snapshot.rs` for how they are kept and `src/ui/panels/history.rs` for what is drawn.

- **A step is the project, less the session.** Each change to what the project holds (a file or content added or removed, a build added, edited, taken or left out, a link or an unlink, a file located, a button pinned, a clothing content added, the workspace the file opens on, an import) keeps the project as its file would state it, without the tabs that are open and the one in front. Undo, Redo and a rollback to any step read a step back, so no step depends on another, and the first change of a project keeps the project as it was opened as the first step (`undoing_add_content_puts_the_project_file_back_byte_for_byte_and_redo_does_it_again`, `a_rollback_restores_an_earlier_step_and_the_steps_after_it_stay_to_be_gone_forward_to`). A drag changes a number on every frame and is one step, said when it is let go (`a_drag_of_a_ceiling_is_one_step_whatever_the_number_of_frames`).
- **It outlives the session.** The steps are in `.openrage/projects/<name of the project file>/history` beside the project file, a file for each step and an index, and the folder ignores itself (a `*` in its own `.gitignore`), so Git never sees it. The newest 200 are kept. The folder is named for the project file and not for the folder it is in, so two project files in one folder (a Save project as where the dialog starts) keep a history and a list of outside files each (`two_project_files_in_one_folder_keep_their_own_history_and_their_own_outside_files`); the history of an earlier build, which sat in `.openrage/history`, is not read. A project opened again lists them; a project file that is not the one the last step holds, because a pull changed it, is a step of its own, `The project file changed outside OpenRage`, and Undo goes back to what OpenRage last held (`the_history_of_a_project_is_there_when_it_is_opened_again_and_still_rolls_back`, `the_history_folder_is_ignored_by_git_and_a_project_file_edited_outside_is_a_step_of_its_own`). History is best effort: a folder that cannot be written costs the project its Undo and a warning once, never a change. The store knows only bytes and labels, which is why the Wardrobe's packs can use it. ⚠ One window is a project's writer: a second window on a project another holds only reads it and keeps no steps of its own.
- **Where Undo is.** Project ▸ Undo project change and Redo project change, and the palette, name the step they move over. Edit ▸ Undo and Redo, and their keys, are the project's while the Project workspace is on screen, the clothes' and the project's together while the Wardrobe is (the newer of the two first), and the document's everywhere else; the Wardrobe also keeps its own Undo clothes change and Redo clothes change. The History panel of the Project workspace lists the steps newest first, with the one the project stands at selected, the steps that were undone dim and in italic, and a disk beside the one the project file holds; a click goes back or forward to it (`a_click_on_a_step_of_the_history_goes_back_to_it_and_a_click_on_a_later_one_goes_forward`), and a click that would take back an import first asks, naming the source folders that go with it (`a_click_on_an_earlier_history_row_that_removes_an_imports_sources_asks_first`). Builds and compiles are lines of the same list that no click moves to: a dot marks the steps a click goes back to, and a run of compiles one after another is one line, *Compiled 5 sources* (`a_run_of_compiles_is_one_line_and_the_steps_between_the_runs_stay_lines_of_their_own`). A click that would take back an import asks *Go back in the History*, counting what it removes (*It removes 5 source folders and 1 file from your project folder*), saying that the game files are not touched and that importing them again brings them back, and its button says what it does, *Remove them and go back* (`the_question_before_going_back_over_an_import_counts_what_it_deletes_in_plain_words`). Removing a file from the project has no toast button that runs out: its step is there as long as the history is (`removing_a_file_has_no_ten_second_button_and_undo_puts_it_back_in_its_place`).
- **An import is a step of the same stack.** The step keeps beside it what its import created (`.attached` in the history folder, which goes when the step does), so Undo, or a click on an earlier step, over any import takes back that import's own folders and files, one import or several, in this session or after the project was opened again (`undo_takes_back_the_import_of_its_own_step_and_not_only_the_last_one`, `a_rollback_over_two_imports_takes_back_both`, `an_import_of_an_earlier_session_is_taken_back_and_a_source_changed_since_refuses_it`). A source changed since its import refuses the whole move, and nothing moves or is removed (`a_rollback_over_two_imports_changes_nothing_when_the_older_one_was_edited`); one that is gone already counts as taken back (`a_source_gone_already_does_not_hold_the_history_back`). Going back over an import keeps a copy of what it made beside its step before it takes it away, and going forward over it puts that back, byte for byte, so Redo makes the import again (`redo_makes_the_sources_of_an_import_again_exactly_and_undo_can_take_them_back_again`, `an_import_is_a_step_of_the_same_stack_which_undo_takes_back_and_redo_makes_again`, `a_file_an_import_kept_goes_with_its_step_and_comes_back_with_it_going_forward`); the copy goes with the step when a new change drops it (`a_step_dropped_by_a_new_change_takes_the_copy_of_its_import_with_it`). Where no copy is kept, an import taken back before copies were kept, the project moves and no more and a toast says to import the files again with Import game files… (`where_no_copy_was_kept_redo_still_says_the_import_is_not_made_again`), and the steps after the import are reached all the same (`a_step_after_an_import_is_still_reached_once_the_history_has_gone_back_past_it`).
- **A save writes what the person changed.** The workspace in the project file is the one the file states, and switching workspace changes nothing in it: Project ▸ Properties and sharing ▸ Start this project on this workspace writes the one on screen, as a step that Undo takes back, and a project made by saving a session states the workspace on screen. - **A shared file names no path of this machine.** A file outside the project's folder has no path another machine could use, so it is not in the project file: it is kept in `machine.json` in the project file's folder of `.openrage` (`.openrage/projects/<name of the project file>`), with its tab open as it was, and comes back when the project is read on this machine (`a_project_file_carries_no_absolute_path_of_this_machine_and_the_files_it_cannot_name_come_back`). - **Close project never waits for a build.** The build finishes on its worker and stands, or leaves the previous build as it was.
