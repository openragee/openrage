# Project model design

How an OpenRage project holds several kinds of content (clothing, maps, weapons) and ships it as one resource or several: modules, outputs, links and templates.

Status: proposal of 2026-10-07. The owner chose the screen words (Content for a module, Builds for an output), one project per window with a second window for a second project, and gave go to [Workbench_Plan.md](Workbench_Plan.md); [Workbench_UX_Design.md](Workbench_UX_Design.md) draws the screens. [R48](Roadmap.md#r48-projects) and its project file stand until a wave rewrites them. The container, the build plan, the targets, links, adoption and templates, and the extension kinds and the second kind of content are built: see [what the container builds](#what-the-container-builds), [what the build plan builds](#what-the-build-plan-builds), [what the targets build](#what-the-targets-build) [what links, adoption and templates build](#what-links-adoption-and-templates-build) and [what the extension and the second kind of content build](#what-the-extension-and-the-second-kind-of-content-build).

## Verdict

A project has no type. It holds **modules**, which have one, and it declares its **outputs**, which say what ships and from which modules. A module can be a **link** to a module that lives in another project. A **template** is only a starting set of modules, outputs and layout.

This takes the owner's three ideas together, because each solves a problem the others leave open:

| Idea | What it solves | Where it lands |
|---|---|---|
| One project with several bricks, templates and no types | One preview, one validation, one budget for everything that ships together | The base: a project holds modules |
| Configure the build when building, grafting other projects in | Shipping the same content in different shapes | Outputs, stored in the project and checked all the time, so nothing is second class |
| Separate projects joined by a mega-project | Reuse across projects, a team with one owner per module | Links: a mega-project is a project whose modules are links |

It is the Visual Studio model with one level less: the solution and the project are the same thing, and what is typed is what the project contains.

## Where the project stands today

The project file is `.openrage-proj` at `PROJECT_SCHEMA` 3 (`src/state/project.rs`): a workspace, the open tabs and the member documents, beside a `vfs/` folder that the virtual filesystem reads ahead of the install. [R48](Roadmap.md#r48-projects) describes it as membership "across every editable type", so it is already untyped. A key a build does not know is carried and written back, which is what lets this model add keys without breaking an older file.

## The questions it answers

- Build maps and clothes into one FiveM resource.
- Build one project into several resources, for size or for update cadence.
- Reuse a module in several projects, and join several projects into one build.
- Start empty, or from a template, with no project type to choose.

## Three ideas compared

| | Separate projects and a mega-project | Grafting at build time | One project, several modules |
|---|---|---|---|
| One preview, one validation, one budget | no | no, everything is found at build | yes |
| Reuse a module elsewhere | yes | by hand | no, unless modules can be links |
| One resource from several modules | yes | yes | yes |
| One module spread over several resources | awkward | redone at every build | yes, it is an output |
| Main flaw | Two levels to learn; conflicts found late | The composition is not stored, so a build cannot be reproduced | A monolith with no reuse |

Content that is shared between modules (a logo on a shirt and on a sign, one memory budget, one ped standing in front of one building) is what justifies the single project. Content reused between projects is what justifies links. How content ships is what justifies outputs.

## The model

| Term | Meaning |
|---|---|
| Project | A folder and a project file. Untyped. Holds modules and outputs, and the documents it already holds |
| Module | A typed part of a project: clothing, map, weapons, files. A folder with its own manifest and data. Brings its own workspace, rules and contributions |
| Output | A named thing to build, declared in the project: its kind (FiveM resource, singleplayer DLC, installer), its name, the modules it takes and its options |
| Link | A module whose folder lives in another project, by path |
| Template | Data: modules, outputs, layout and rule overrides. Applied once; the project records where it came from and nothing else |
| Contribution | What a module hands to one kind of output: files, manifest entries, metadata documents, budget figures, diagnostics |
| Plan | What an output merges its modules' contributions into, as data, before anything is written |

Visual Studio's names, for the reader who knows it:

| Visual Studio | Here |
|---|---|
| Solution, blank or not | Project |
| Typed projects | Modules |
| Project references | Links |
| Build configurations and packaging projects | Outputs |
| New project templates | Templates |

### Rules

1. **The project has no type; a module has one.** An empty project is a project with no module, which is what a project is today.
2. **A module is a folder with its own manifest.** It loads on demand, so a large project opens on an index of names, counts and cached problems.
3. **An output is declared in the project and checked all the time.** Its plan runs in the background and its problems join the problems list.
4. **A module contributes; an output merges.** The merge detects collisions, adds the budgets, and the executor writes the plan and reads back what it wrote.
5. **Validation has two levels.** A module's problems concern its own content; an output's concern what its modules do together.
6. **A link is edited at its source.** The including project shows a banner, only the including project's outputs count, and a module has one writer at a time.
7. **A template is a file anyone can share.** It holds no code.
8. **Complexity appears when it is needed.** A project with one module and one output shows a Build button; the outputs editor appears from two modules or two outputs.
9. **A machine's paths stay out of the project.** The folder a build is copied to is a setting of the machine, so a project shared in Git carries none, and neither does a file the project cannot name relative to its own folder: a save keeps such a document in `machine.json` in the project file's own folder of `.openrage`, beside the project and out of Git, and the workspace the file states changes only when the person says the project opens there ([what project history builds](Workbench_UX_Design.md#what-project-history-builds)).

## Combining and splitting

An output of several modules combines their contributions; the plan decides what is allowed.

- Some manifest keys describe the whole resource and must agree between modules, such as the manifest version and the games it targets. Others add up: data files, scripts, file lists. The merge policy is per key.
- A module chooses the paths of its files, because FiveM finds `stream/` at the root of a resource and a folder of its own would hide a module's streamed files from it; the plan refuses two modules that write one path instead of keeping them apart by construction. It also checks the names the game resolves globally, such as a clothing collection or an archetype, across every module of the project, even when an output splits ([what the build plan builds](#what-the-build-plan-builds)).
- Budgets add up across modules: files, size, metadata entries, estimated memory.

An output can also split. Over a size limit it divides at module boundaries into several resources; or a module becomes an output of its own. Combining and splitting are options of an output, never a redesign of the content.

⚠ A combined resource restarts and updates as one unit. Whether server owners prefer separate resources for that reason is not measured here, so a combined output is a choice the project makes and not a default, and the same project can declare both a combined output and a split one.

## What a module hands to an output

Each module type declares which kinds of output it supports and what it contributes to each. A module type that cannot ship in an output kind says so, and the outputs editor shows that cell locked with the reason: scripts cannot ship in a DLC, for example. The contract is built ([what the build plan builds](#what-the-build-plan-builds)) and is internal to OpenRage until the plugin boundary has a use for it; a plugin may later add contributions, validators, output post-processors and templates as data in and data out ([Plugin_ABI.md](../reference/Plugin_ABI.md)).

The first module types, in the order they are built:

| Module type | Holds | Notes |
|---|---|---|
| Files | Loose files copied as they are: scripts, interface files, configuration | Built: it holds the project's documents, so it has no folder of its own |
| Clothing | The Wardrobe model of [Clothing_Tool_Design.md](Clothing_Tool_Design.md) | The first typed module. Built: `or-project` knows the kind and its folder, and `or-wardrobe` contributes for it ([what the engine builds](Clothing_Tool_Design.md#what-the-engine-builds)); the Wardrobe workspace draws and edits it ([what the Wardrobe workspace builds](Workbench_UX_Design.md#what-the-wardrobe-workspace-builds)) |
| Map | The documents of a map or an interior, and their packaging | The editing itself stays a plugin ([R47](Roadmap.md#r47-the-plugin-slate-after-the-first)). Drafted, not built: [the Maps view](Workbench_Views_Design.md#maps) |
| Weapons | Weapon metadata and models | Drafted, not built: [the Weapons view](Workbench_Views_Design.md#weapons) |
| Addon ped | A ped with its component set | Shares the ped metadata family with clothing; the second type extracted the shared substrate. Built: [what the extension and the second kind of content build](#what-the-extension-and-the-second-kind-of-content-build) |

## What the container builds

The Files module and one kind of output, a FiveM resource, are built in `crates/domain/or-project`, and the project file is schema 4; the other two kinds of output and the target of an output are [what the targets build](#what-the-targets-build). Of the illustration above, `modules` and `outputs` are the keys, `files` and `clothing` the module types and `fivem-resource` the output kind and `link` the key of a linked content ([what links build](#what-links-adoption-and-templates-build)); the other module types are not built.

```
"modules": [ { "id": "files", "type": "files" } ],
"outputs": [ { "id": "fivem", "kind": "fivem-resource", "name": "police_pack",
               "take": ["files"], "max_bytes": 1073741824 } ]
```

- **A project of today is a Files module.** A file with no `modules` key reads as one over its documents and gains the keys when the editor saves it. A module or output of a type this build does not know is carried, and a plan refuses it.
- **The plan is data.** `plan` takes the container and what the caller saw of each file and lists the files a build will copy or cook and the one document it writes, `fxmanifest.lua`, unless the project holds its own. A module's contribution may also hand over files the module generates (`Origin::Document` for text, `Origin::Generated` for bytes such as a metadata file), which a build writes as given and reloads through the reader of their extension, a `.ymt` included. A file keeps its path inside the project folder; a file outside it, under `build/`, missing, or sharing a path with another in all but case, is a problem and a plan with a problem is not built. An output may declare `max_files` and `max_bytes`, and exceeding one is a problem too.
- **A build never damages the last good one.** It writes `build/<name>` through a hidden `.new` folder, reads every file back, byte for byte and through the declared reader where one reads the extension, swaps it in and keeps the build it replaced as `.previous`. Two builds of one project are byte-identical, and `--out` names another folder for one run, so the project stores no path of a machine. **A build never damages a source:** it refuses a folder that is the project, holds it, is inside it but for `build/`, or is or holds a file it copies, and refuses to replace a folder it did not build, which a hidden `.<name>.openrage-build` beside a build says it did.
- **Not built:** anything that says a pack loads in game, and any kind of content but Files, Clothing, Addon ped, Weapons, Particles and Maps. A clothing, addon ped, weapons, particles or maps module is a kind this crate knows and keeps the folder of (`ModuleKind::Weapons`, written `weapons`, with a `weapons.json`: [what wave P42 built for Weapons](Workbench_Views_Design.md#what-wave-p42-built-for-weapons); `ModuleKind::Particles`, written `particles`, with an `effects.json`: [what wave P43 built for Particles](Workbench_Views_Design.md#what-wave-p43-built-for-particles); `ModuleKind::Maps`, written `maps`, with a `maps.json`: [what wave P44 built for Maps](Workbench_Views_Design.md#what-wave-p44-built-for-maps)); its contributions come from `or-wardrobe`, `or-addonped`, `or-weapons` and `or-particles`, which depend on this crate and not the other way round, and `or-content` lists the kinds and hands their contributions to `plan_with` beside `files_contributions`.

`openrage-cli project create`, `add-content`, `add-build`, `set-build`, `set-file-type`, `remove-build`, `plan`, `build`, `verify`, `clean` and `redirects` keep a project and run its builds without the editor, with `--build <id>` naming a build (`--output` is the older spelling of it, still read and not shown in the usage), and `adopt`, `link`, `unlink`, `links` and `template` run [what links, adoption and templates build](#what-links-adoption-and-templates-build); none of them is a route of the `serve` protocol ([CLI_Server_Protocol.md](../reference/CLI_Server_Protocol.md#what-is-not-a-route)). `create` makes the `sources/` folder beside the project file and records the game (`legacy`, `enhanced` or `both`, the default) in the file, as New project does, and a build that states no edition ships for the game's own. The editor runs the same build and a Clean that removes what a build left, which `or_project::clean` does only where the hidden marker says OpenRage built it; the Project workspace is [Workbench_UX_Design.md](Workbench_UX_Design.md)'s `What the Project workspace builds`.

## What the build plan builds

Wave D of [Workbench_Plan.md](Workbench_Plan.md) made the plan the one place that content plugs into, in `crates/domain/or-project`. The Files module is its first contributor and goes through the same path, so a kind of content that arrives later adds data and no second route.

- **A contribution is data.** A `Contribution` holds what one module hands to an output: its files and documents at their paths inside the resource, lines for the manifest, names it claims, named figures, items with stable ids, and its own problems. `plan_with` takes one for each module the caller can build, and `plan` is `plan_with` over what the Files module contributes. A module the output takes and nobody contributed for is refused, whatever its kind; `plan` always hands over one for every Files module, so only a caller of `plan_with` can meet it.
- **The merge policy is per manifest key.** `fx_version` and `game` describe the whole resource, so every module that states one must state the same value and the build supplies `cerulean` and `gta5` when none does. Any other key adds up: the lines are sorted and written once, so two builds are byte-identical whichever module came first. A resource that holds its own `fxmanifest.lua` takes no lines from a module, because a build does not edit it.
- **Names the game resolves once are one namespace for the project.** A claim is a kind and a name, compared without regard to case as the game hashes it. Two claims of one name are a problem of every output that takes a module holding one of them, including a claim by a module that output leaves out, so splitting an output never hides a clash. Two modules that write one path are refused naming both.
- **Budgets are figures against limits stored as data.** A module's figures add up by name against the output's `limits` map, beside `max_files` and `max_bytes`, which keep the plan's own totals; `files` and `bytes` are not figure names. `Plan::budgets` says each figure with its ceiling.
- **An output may split.** With `split` set and a ceiling exceeded, `plans` takes the modules in the order of `take` and starts a new resource when the next one would take the current one over a ceiling, so each resource holds one unbroken run of `take`, and it never cuts a module or goes back to an earlier resource. Packing each module into the first resource with room would use fewer resources where a small module follows a large one, at the cost of runs that are no longer unbroken; that is not built. The resources are `<name>_1`, `<name>_2` and so on, each planned as an output of its own with the claims of the whole project still checked. A module over a ceiling by itself is a problem of its own resource, and so is any project whose only content cannot be divided. `build_all`, which `openrage-cli project build` calls, checks every resource of a split against the build folder before it writes the first, so a plan problem or a folder OpenRage did not build stops the whole set with nothing written. A failure while one resource is written (a source that changed, an I/O error, a file that does not read back) stops there, and the resources before it stay built, because each is swapped in on its own.
- **A build is edited as data, by the window and by the command line alike.** `Container::edit_build` changes one build (its name, kind and edition, the content it takes, `split`, `max_files`, `max_bytes`, a named figure's ceiling in `limits`, `ship_unchanged`) and refuses, changing nothing, a name that cannot name a folder or that another build writes, content the project does not hold or a build takes twice, and a figure named for one of the totals; the id never changes, so a rename keeps what points at the build. `Container::set_taken` ticks or unticks one content of one build and keeps the order of the project's content, unless the build's order was chosen, since a split cuts in the order of `take`. `Module::set_file_type` states the type a singleplayer DLC registers a file as, on the project's own Files content only. A new build is offered a name that is free and that no split reads as one of its resources: `Container::free_build_name` names it for the project, then for what it is (`<name>_dlc`, `<name>_oiv`, `<name>_enhanced`) and numbers it `_v2` after that, never `_2`, which is where a split writes its second resource (`reads_as_a_part` says when a name is spelt like one). A split for update cadence is two builds over different contents, which share no file, and `split` with a ceiling is one build cut between contents.
- **A kind of build says which content it cannot ship.** `cannot_ship` reads what a content contributes against a kind of build and gives the sentence of the refusal the plan would make: a singleplayer DLC has no manifest and runs no script, so a content that adds a manifest line other than `data_file`, or holds a file whose type the game is told by nothing (a script, or any file that is not in an `x.rpf` folder and not an `.ityp`, unless a `data_file` line or the Files content's `file_types` states one), cannot ship in one. The Builds window locks that cell of the matrix and shows the reason; it is the rule of `finish` in the DLC writer read for one content, so a type that another content states for this content's file is not counted.
- **A source folder is a cook.** The Files module's contribution also holds each `.src` folder of the project as a file at `stream/<name>.<ext>` (`Origin::Cook`), and the folder and everything in it never ship. This crate knows no kind of source: the caller reads each `asset.json` into a `SourceFolder` and hands `build_with` the cook, so the editor and `openrage-cli project build` cook with `or-source` and a test hands in a stand-in. The executor cooks every source into a hidden `.<resource>.cook` folder before it writes anything, so a source that fails stops the build with every failure named and the last build as it was; it moves a cooked file to the output's target as it moves a copied one, and a build of any kind leaves out a source of the game's own content that is still the game's file unless the output's `ship_unchanged` is true (`Built::unchanged` lists them; a pack and a package are written again from what remains). Two sources that cook one file are a problem that names both. [How a build cooks](Source_Format_Design.md#how-a-build-cooks) says what the cook is and what it measured.
- **A build says what it checked as data.** `Verification` is what `verify` finds when it reads a written folder back, and the Build tab draws it: `reloaded` holds every file a reader reopened and is never cut short, with `reload_line()` for the count (files compared, reloaded, read by no reader); `metadata()` counts the metadata documents reloaded by what they are, with the elements of the arrays their root holds; `names` is the plan's `NameCheck`, which counts the names the game resolves once that the build holds by kind and keeps the clashes, and says so in a line when none is held twice; `memory` is the pages the game allocates for the RSC7 files written, summed from their own headers (virtual and physical page sizes, an estimate of what streaming them in takes and no more), against the build's `limits` entry `memory`, and over it is a problem that stops the build with the last good one in place; and `reproducible` says whether a second build wrote the same bytes. That second build is made on request only, by `check_reproducible`, into a hidden `.<resource>.again` folder that is compared byte for byte and removed, so the live build is never touched; it cooks every source again, which is what finds a cook that stamps a time or a random value into its file. The command line asks for it with `build --reproducible` and exits with a failure when it differs. Nothing in it says a build loads in game.
- **A build says which step it is on.** `build_observed` and `build_all_observed` are `build_with` and `build_all_with` that call an observer as the build enters each `BuildStep` (cook what changed, write to a fresh folder, read every file back, swap it in), once per resource of a split output; a build that stops reports no step it never reached. The plan is the caller's step and comes first, so the app's job and its Build tab count five. Nothing about a step is kept: it is what a screen shows while a build runs.
- **A sentence says Content and Build.** What a person reads about a plan, a project file, a merge or a build says Content and Build and never module or output; those are the code's words, and a test reads the string literals of the files that write the sentences (`no_sentence_of_a_plan_a_container_a_merge_or_a_build_holds_module_or_output`). Files that need a type in a singleplayer DLC are one problem with a count and three names, not one problem each.
- **The diff follows stable ids.** A module's items carry an id that survives a rename, the name the game sees and a digest of the content. `diff` reports an id that is new, one whose digest changed, one whose name moved and one that is gone, and an item that both moved and changed is in both lists; a new item that takes a name another left is not a move. `Diff::redirect_map` exports every move as a canonical JSON document, old name to new name by id. A build records its items in a hidden `.<resource>.openrage-items.json` beside the resource after the swap, so a failed build leaves the last good build's record, and `since_last_build` and `Built::since` read it. A record that cannot be read is no record.
- **Not built:** the Files module contributes no items, since a loose file has no id that outlives a rename, so a project of loose files has an empty diff. The clothing module is the contributor of items, claims and figures, and the checks that hand a contribution in as data still hold the contract for a kind that does not exist. `openrage-cli wardrobe diff --redirects` and `openrage-cli project redirects --file` export the redirect map of what the next build will move, from the items the last build recorded; run it before that build, since a build records its own items. A build never removes a resource that an earlier split or an earlier name left in `build/`, and a build that divides differently from the last one has no record to differ from, so the screen's Clean is the way to start over: it finds every resource in `build/` by its hidden marker with `or_project::built_resources`, whether or not an output declares it now, and removes it with its record.

## What the targets build

Wave J of [Workbench_Plan.md](Workbench_Plan.md) gave an output two more choices, in `crates/domain/or-project`: what it writes and for which edition. A build of every kind lands the same way, as a folder named for the output under `build/`, written fresh, read back, swapped in and recorded, so nothing in [what the container builds](#what-the-container-builds) changes.

- **Three kinds.** `fivem-resource` (the screen says FiveM resource), `singleplayer-dlc` and `oiv-package`. The plan lists the same data for each, and the kind decides the documents the build adds and how the files are written and read back.
- **A singleplayer DLC** is `<name>/dlc.rpf` and nothing else, so the folder is what an install copies in. Its plan lists `setup2.xml` and `content.xml` as documents, which `or_title::dlc::build_pack` (the call `openrage-cli dlc create` makes) writes into the archive, and carries the line `dlclist.xml` needs (`Plan::dlclist_entry`). The game is told a type for each file it registers, and no extension but two settles one ([Dlc_Pack_Creation.md](../features/Dlc_Pack_Creation.md)), so a file registers with the type that a `data_file 'TYPE' 'path'` manifest line states, the form a FiveM manifest states it in, else `.ityp` and `.rpf` by their extension, and any other file refuses the plan by name. Content contributes those lines, and the Files content states them as `file_types` on its entry in the project file, a map from a path inside the project to a type such as `HANDLING_FILE`, which the Builds window (File types) and `openrage-cli project set-file-type` set. A document a content writes, such as a `.meta` it generates, ships in the pack as a file does and registers by the same rule. A path that runs through a folder named `x.rpf` is a file inside that archive: the build packs the archive, nested to any depth, and the pack registers the archive as `RPF_FILE` and not what is inside. Any other manifest line refuses the plan, since a pack runs no script. The pack name is a device name as well, so it is `[A-Za-z0-9_]`, and the order, the minor order and the type of pack are `dlc create`'s defaults (255, 0, a compatibility pack); no key sets them yet. Reading it back opens the archive and each one inside it, compares every file with the plan and finds one missing, one extra or one that differs. The plan counts what each archive of the pack would hold, a file, a nested archive and a folder as one entry each and an archive with a root, keeps the fullest as the budget `archive_entries` and refuses a pack over the 65,535 an archive holds (the figure the clothing tools state, which nothing here measures) or over a lower ceiling the build sets for it; `split` divides an output at content boundaries into packs `<name>_1`, `<name>_2`, and a content over the figure by itself is refused with the sentence that a split divides between contents and not inside one. Planning 70,000 files had been quadratic in the number of files (14 s); it is a hash lookup now (0.3 s).
- **An OIV package** is `<name>/<name>.oiv`, a stored zip that holds `assembly.xml` and each file under `content/` at the path it installs to. The manifest adds each file, inside the archives its path runs through (every folder on the way named `x.rpf`), and its author, version (`major.minor`) and description are keys on the output's entry, which the container carries. It is written by `or_title::oiv`, from the 2.2 shape as the author knows it, with no OpenIV to install it, so reading it back means the zip holds the manifest and each file the plan names, equal to the plan, and that the manifest adds only what the zip holds. It writes no command but add, and a file named `assembly.xml` refuses the plan. A content whose files are those of a pack (`Contribution::pack`, which the clothing content sets for a pack and a package) is installed below `update/x64/dlcpacks/<name>/dlc.rpf`, with the `setup2.xml` and `content.xml` that register it, the entries of its archives counted as a pack's are, and a note that the package edits no `dlclist.xml`; the files of any other content land where they always did.
- **Words, options and what reads a build back.** A FiveM manifest states the `author`, `description` and `version` of the build's entry after `fx_version` and `game`; a kind of content may shape its files by the build it is taken by (`Content::contribution_for`), which is how a clothing pack is flat in an archive for a pack and has its options ([what the engine builds](Clothing_Tool_Design.md#what-the-engine-builds)); and `or_project::built_files` reads a file of a build by the path it has in the plan whether the build is a folder, a `dlc.rpf` or an `.oiv`, so a kind of content checks what only it knows without caring which.
- **Progress and stop.** `build_watched` and `build_all_watched` take an `or_project::Watch` (an `or_job::Progress` and an `or_job::Cancel`): the build says the file it is on and how many bytes of its plan are done while it cooks, writes and reads back, and a stop between two files removes the folder it was writing and returns `BuildError::Stopped` with the live build untouched. Once the folders are swapped there is nothing to stop. The editor's Jobs list and `openrage-cli`'s Ctrl+C set it.
- **A target** is `legacy` or `enhanced` on an output, and absent means each file ships as authored. The plan marks each `.ydr`, `.ytd`, `.ydd` and `.yft` of an output that has one as a retarget, and the build moves it to that layout through `or_io::gta5::retarget::retarget_file`, or copies it exactly when its own RSC7 version is there already. A file the other layout cannot describe stops the build with its name (`BuildError::Retargeting`) and leaves the last good build, since carrying it unchanged would ship bytes that mean something else. What the target has no field for is dropped and named in `Built::losses`. ⚠ A drawable's material parameters are respelled through a shader database, which `build_with` takes and nothing ships; with none, every parameter of a moved drawable is dropped and named, as `convert retarget` does. A retarget's size in the plan is its source's, since the moved file's is not known before it is made, so a ceiling counts the source. Reading it back checks that the file reloads and is in the layout the output ships, and cannot compare it with its source. "Both editions" is two outputs.
- **Not built:** the delete, replace and patch commands of a package, the order and type of a pack as keys, and any claim that a pack loads in game or that OpenIV installs a package.

## What links, adoption and templates build

Wave K of [Workbench_Plan.md](Workbench_Plan.md) built the three ideas the study left for last, in `crates/domain/or-project` (`links`, `adopt`, `template`), with the clothing recogniser in `crates/domain/or-wardrobe` (`adopt`) and the verbs in `openrage-cli project`. The screens are [Workbench_UX_Design.md](Workbench_UX_Design.md)'s.

- **A link is a content whose folder lives somewhere else.** It is a module entry with `"link": true` and a `path` that may leave the project's folder: relative with `..` where the two share a root (`../brand_kit/modules/logos`, so a pair of sibling folders travels together), and absolute only where no `..` reaches, which is another drive. A pack of clothing or addon peds is linked by its folder (an `addonped.json` is what makes a folder one). A Files content is the files a project's file lists, so it is linked by the folder of the project that holds them: the `path` leads to a folder with a `.openrage-proj` in it, whose Files content of its own (the first that is not a link) hands its documents, its `file_types` and the `.src` folders found under that folder to the including project's build, at the paths they have in that project. `links::add_link` refuses a folder that is not there, one inside the project (it is the project's own content and needs no link), one around it, one already linked as the same kind of content (an adopted project is a Files content and a pack in one folder, and both are linked), one that no recogniser knows as content, and a Files link to a folder with no project file or a project with no Files content, and otherwise adds the entry and puts it in the `take` of every build, since a content no build takes ships nowhere; `remove_link` takes the entry and those takes out and touches no file. `links::add_project_links` links a whole project at once, its Files content by the folder and each pack it holds by its own, all or nothing, and names the links that project holds itself in `Linked::not_followed` without linking them. A link names a folder and not another project's links, so nothing is followed further and there is no cycle: the banner over a link whose project links content of its own says which, and that a link is not followed, so those are not read here. A project made of links alone has no Files content of its own and builds: `files_contributions_with` takes the files of a project from its first Files content that is not a link, and hands a linked one to `links::linked_files`; a caller adds `links::linked_sources` to the source folders it describes, so a linked project's sources are cooked as its own are.
- **A link has one writer.** The project that holds the folder is the only one that writes it: the nearest folder at or above it that holds a `.openrage-proj` names that project (`Link::owner`), and the including project reads the folder into its own builds and writes nothing in it. The files of a linked pack are copied from where the link leads, a build writes only the including project's `build/`, and only the including project's outputs count: its figures, ceilings and claimed names are those of its own plan, and a name the game resolves once is still refused across its linked content and its own. Anything that edits a pack asks `or_wardrobe::module_folder_to_edit` (or `links::refuse_write`) for the folder to write, and a linked one is refused by naming the project that holds it; the Wardrobe workspace asks before every write it makes (`folder_to_edit` in `src/state/workbench/wardrobe.rs`). The banner over a linked content says so (`Link::banner`), and a link whose folder is gone is a problem of the project that says where it led. ⚠ One writer is a rule of the projects and not a lock: a second OpenRage window on the project that holds the pack can edit it while this one reads it, and what a build read is the pack as it was then.
- **A file with no place is said, never added silently.** `links::refuse_member` refuses to add a file outside the project's folder to the Files content, because its place in a resource is not defined, and one inside linked content, which is read through the link already. Add files…, locating a missing file and `openrage-cli project create` ask it; the sentence says to copy the file in or to link its folder. A project file that already holds an outside member still opens, and its plan names the file; so does a file open in a tab, which is a member at the next save wherever it is, though a file outside the folder is kept beside the project for this machine and is not in the file the project shares (`.openrage/machine.json`).
- **Adoption groups what a folder holds by what is recognised in it.** `adopt::analyse` reads a folder and writes nothing. A `Recogniser` is a kind of content that knows its own files, handed in because the content depends on this crate and not the other way round; it takes its files out of the Files content, says what it could not place and may ask for a file of its own to be added beside the folder's. What no content claims is the Files content, exactly as a folder nothing recognises always was: the same walk (not `build/`, `vfs/`, hidden folders, source folders or project files, and 8 folders deep), and no Files content at all when the content took every file. ⚠ The Files content takes at most 10,000 files, counted after the content has taken its own, so a clothing pack of any size keeps its scripts and its interface; the files past the bound, and the folders deeper than the walk reads, are in no content, and the project file lists them (the first thousand of each) with a note that says how many. `Adoption::write` adds the files it asked for, replaces none, and hands back what it added so a caller whose next step fails can take it back (`Written::undo`), and the project file records what was not placed under `adopted`, so the Project workspace can list it after the dialog is gone.
- **The clothing recogniser** is `or_wardrobe::adopt::Clothing`. A `wardrobe.json` already in the folder is the pack; without one the files are imported in place and the pack that comes out is the file the adoption adds. The clothing content has the folder itself as its folder (`.`). The files it ships, the models and textures a garment names, and the metadata and manifest it writes again are not Files content: a metadata file the import read is the pack's own content and is not carried as a loose file, and the `fxmanifest.lua` and a copy of a document the build writes again at the same path (the shop metadata, a variation file) are listed as not carried, since carrying them as loose files too would register one collection twice. What the import could not place (a model whose name states no slot, a cloth with no model at its place or one the game would not find from its model's name, a fragment file, a metadata file no reader opens, a variation file whose name states no ped) stays a loose Files file and is listed, so it ships as it did. ⚠ A line of the old manifest that the content does not state (a script, a file list, a data file) is not carried, and the listing says so; `openrage-cli project` and the dialog name it, and nothing compares it for you.
- **A mapping that comes in is adopted into a new folder.** `openrage-cli project adopt <mapping.zip|folder> --into <folder>` reads a folder or a zip archive as a place (`or_project::place`), which it never changes, and `or_maps::mapping` makes a project of one resource or loose stream folder of it: the map files, type files, models and textures under `stream/` become sources of a maps content, every other file is kept whole at its place as Files content, a file an asset escrow locks is kept whole and counted, and the resource's manifest is kept beside the project while a build writes its own. The report says all of it before anything is written, with the lines of the manifest a build does not carry and what the map rules find. ⚠ A zip is listed from its directory and unpacked only by the adoption, into a hidden staging folder inside the new project; an archive that is not safe to unpack is refused whole, by the entry, and the limits it is held to are data with their reasons (`LIMITS`).
- **A template is a file that holds no code.** `<name>.openrage-template` is canonical JSON: a format word and a schema, a name and a description, the workspace the project opens on, the buttons it shows, the game, and the `modules` and `outputs` keys of a project file. A template made from a project drops what only one machine or one project can mean: a link, and the `file_types` of a Files content that name its files. The first build is named `{resource}` and every other `{resource}_<id>`, so applying it fills the new project's resource name in; a build keeps the ceilings, the split, the limits, the kind and the edition it had. A template from somebody else is read field by field, refuses a newer schema, and drops a content whose folder is not a plain folder inside the project or that is a link, so applying one never writes outside the new project's folder. A project made from it records the template's name under `template` and nothing else of it, and a clothing content starts as its folder with an empty pack.
- **The game is the edition a new build ships for.** The project's `game` key (Legacy, Enhanced or Both) is the target a new build takes when it states none: Legacy and Enhanced name their own, Both leaves a build as authored. A build that states its own edition keeps it.
- **Where it shows.** The verbs `openrage-cli project adopt`, `link`, `unlink`, `links`, `template` and `create --template` run all of it without the editor; the app's are [what the front door builds](Workbench_UX_Design.md#what-the-front-door-builds) and [what the Project workspace builds](Workbench_UX_Design.md#what-the-project-workspace-builds).
- **Not built:** a link followed to the links of the project that holds it, a lock that makes two windows agree on a writer, a template that carries rules, waivers or files, a place for shared templates other than the folder beside the preferences and a file somebody picks, and the Wardrobe workspace's planning of linked or adopted clothing in the app: the Project workspace still reports a clothing content as one nobody contributed for, and `openrage-cli project build` builds it.

## What references build

Wave P33 of [Workbench_Plan.md](Workbench_Plan.md) made a project hold sources only, so what a content needs and the project does not hold is data too: a reference, in `crates/domain/or-project` (`reference`), read by the Wardrobe through `or_wardrobe::follow`.

- **A reference is a small file.** `<name>.ref.json` in the content's folder, canonical JSON with a format word (`openrage-reference`), a schema and a `form`: `here` (a source or a file of this project, by its path and, for a source, by its asset id), `other` (a source or a file of another project, by that project's folder stored as a link stores it, then the path and the id) and `by_id` (a name or a hash typed by hand). A file of another format, a newer schema or a path that leaves the project is refused (`a_reference_is_a_small_json_file_that_reads_back_in_each_form`, `a_file_of_another_format_or_a_newer_schema_or_a_path_that_leaves_the_project_is_refused`).
- **It is resolved when a plan is made.** `reference::resolve` leads a `here` reference to the source whose id it states, wherever the folder has been renamed or moved to, and one without an id to its path; an `other` reference is resolved in the project that holds it, found as a link's owner is (`a_reference_to_a_source_of_the_project_follows_a_rename_and_one_to_a_file_follows_the_path`, `a_reference_to_another_project_is_stored_by_path_as_a_link_is_and_resolved_there`, `the_project_that_holds_a_content_folder_is_the_nearest_one_above_it`). A source whose id is gone is unresolved and says which id (`a_source_whose_id_is_gone_is_unresolved_and_says_which_id`).
- **An id alone ships no file.** The build names the id, and the plan carries a plain sentence in `Plan::notes` that the file is not in the project, which `openrage-cli project plan` and the Build tab print (`an_id_reference_resolves_to_the_id_and_the_plan_says_in_a_sentence_that_the_file_is_not_in_the_project`).
- **A content owns the sources in its folder.** A source folder inside the folder of a content that is not Files belongs to that content (`or_project::content::content_owning`): the Files content does not ship it, and one no garment names is the content's, not shipped by any build.
- **Not built:** a reference to a folder of sources, a reference stored as a key of the project file, and following the references of a linked content into the project that holds it.

## What the extension and the second kind of content build

Wave L of [Workbench_Plan.md](Workbench_Plan.md) built the first kinds of plugin that extend a build and the second kind of content, in `crates/domain/or-plugin`, `or-project`, `or-addonped` and `or-content`. The screens are [Workbench_UX_Design.md](Workbench_UX_Design.md)'s, and the contract of the plugins is [Plugin_ABI.md](../reference/Plugin_ABI.md#a-plugin-that-extends-a-build).

- **A validator and an emitter are data in and data out.** The plan of a build is a JSON document (`Plan::document`, the one `openrage-cli wardrobe plan` prints, which a plugin is handed as `Plan::guest_document` without where on the disk each file is copied from), a validator reports findings about it one call at a time and an emitter adds text files, and a plugin that does either is run by the app over each plan its scan and a build make (`src/state/plugins/extensions.rs`). An error a validator reports is a problem of the plan, so the build is refused; a warning is in the Problems list; an emitter's files join a FiveM resource's plan through `Plan::with_emitted`, which refuses a path that leaves the resource, a path in `stream/` and one that differs from another file's in case alone, and which says of any other kind of output that it would have to register each file. A plugin that stops, or is refused a call, costs itself and is a warning of the build. The plugin adds a rule or a file with no change inside the app, which `src/state/workbench/scan/a_plugin_extends_what_a_project_builds.rs` shows by installing one beside it.
- **The cloth painter is the first plugin** ([R46](Roadmap.md#r46-first-plugin-a-clothing-tool-on-openrage)): `plugins/cloth-painter`, described in [plugins/README.md](../../plugins/README.md#the-cloth-painter).
- **The addon ped is the second kind of content.** `ModuleKind::AddonPed`, written `addon-ped` in the project file, is a folder with an `addonped.json` that lists each ped by a stable id, the name the game resolves it by and the files it is made of. A file named for the ped streams at `stream/<file>` and any other at `stream/<ped>/<file>`, unless the file says where it lands. The data file that defines the peds to the game (`peds.meta`) is shipped as it was written, registered with `data_file 'PED_METADATA_FILE'`, and read for the `Name` of each entry, since no typed root declares the game's structure for a ped's data and a field of it would be written from memory. The rules (`or_addonped::RULES`) stop a build for a name that is not a lower case name, two peds of one name, a ped with no model, a model that streams under another name than the ped's (a waiver with a reason sets that one aside), a file that is missing, escapes the folder or will not open (the data file among them), two files at one place, a file placed outside `stream/`, and a data file with no entry under a ped's name; they warn for a ped with no texture dictionary, a module with no data file and two files with the same bytes. A ped's name is a claimed name of its own kind (`ped model`), so two modules that name one ped are refused across the project, as two collections are, and a clothing collection of the same spelling does not clash with it. Each ped is an item with a stable id, so a diff of two builds follows it through a rename. A folder with no `addonped.json` is adopted for the models its `peds.meta` names and no other, since a vehicle's or a weapon's model is a `.yft` too and its manifest would otherwise be taken out of the Files content. `openrage-cli addonped validate` lists the findings and `addonped verify` reads a build back against the module (each ped's model, the data file and its manifest line, `or_addonped::verify`, which the editor runs after a build too); the plan and the build are `openrage-cli project plan` and `build`.
- **The substrate was extracted when the second kind existed.** What clothing and addon peds both needed moved to `or_project::content` and `or-wardrobe` re-exports it, so every path it had still works: the facts about the files a module names (`facts`), the severity and the shape of a rule (`rule`), the checks a verifier reports (`check`), the folder of a module, a new id, the lower case name and the atomic write of a model (`folder`), and the `Content` trait through which a kind is planned, adopted and started. `or-content` lists the kinds once, so the editor and `openrage-cli` cannot disagree about them. Every clothing suite ran before and after with the same results and none was edited. What stayed in `or-wardrobe` is a finding and the application of waivers, because a clothing finding names its `garment` where a ped's names its `ped`, and tests of the clothing crate read that field. Wave P23 added to the shared parts what a second kind of content may want: a rule may carry a limit (`Rule::with_threshold`), a fact may carry what a measurer a kind hands to `inspect_paths_measured` counted in the file (`Depth::Measure`, remembered with the digest), and `remembered_under` and `remember_from` hand what a session remembered to the next, which `or_wardrobe::cache` keeps in a pack's private folder.
- **Not built:** a plugin that adds a manifest line or a contribution of its own, binary emitted files, an emitter for a singleplayer DLC or a package, and running a plugin from `openrage-cli`, which does not embed the host; writing `peds.meta` from the model, reading a ped's variation metadata against its component files, a template and a workspace for addon peds, a dressed preview of one, and any claim that a ped loads in game.

## Format permanence

[R48](Roadmap.md#r48-projects) warns that project formats are forever, so this model keeps the part that cannot change small.

- The project file gains two keys, modules and outputs. A build that does not read them carries them, so an older build opens a newer project and keeps what it cannot read.
- Each module's data carries its own version and its own migrations, so a new module type never changes the project file's format.
- The member documents the project holds today stay where they are. A project with no module is valid and is what exists now.
- The schema number moves once, to declare the container's new keys.

## The window

The explorer has three tabs: the project, the game's files and the mods overlay. The project tab lists modules, each with its type, its problem count and its link mark, then the outputs. Selecting a module opens its workspace in the middle: the Wardrobe workspace for clothing, the document editors for a map. A module's workspace is a layout preset, as workspaces already are.

- **The start page** offers templates (empty, clothing, map, weapons, a themed pack, a combination of existing projects) and a way to open an existing FiveM resource or DLC folder as a project: OpenRage groups what it recognises into modules and lists what it could not place. Built: Empty project, Files project, Project from a folder, which makes a folder a project, groups what it recognises into content and moves nothing, and any template file another project made ([what the front door builds](Workbench_UX_Design.md#what-the-front-door-builds), [what links, adoption and templates build](#what-links-adoption-and-templates-build)); the other templates wait for their content.
- **Dropping files on a project** proposes the module that fits, so no type is chosen in advance.
- **The scene** shows every module together, with a switch per module.
- **The problems list** names the module or the output each problem belongs to.
- **The outputs editor** is a matrix of modules by outputs with a live size and state per output, the plan of the selected output and its manifest. Built as the Builds window ([Workbench_UX_Design.md](Workbench_UX_Design.md#what-the-project-workspace-builds)): a form for the chosen build (name, kind and edition, split, ceilings, ship unchanged), the matrix with a lock and its reason where a kind of build cannot ship a content, which appears only from two contents or two builds, the types a DLC registers files as, and a new build; the plan shown beside the build is the scan's, so a ceiling set there changes the plan at once. Not built: the manifest beside the matrix.
- **The Build button** builds the active output. The destination on the machine is a setting of the machine.

## Risks

| Risk | Why | Answer |
|---|---|---|
| Over-generalising early | A generic framework fixes a format before a second module type shapes it | Only the container is generic; module types are first-party and each owns its data |
| The outputs matrix is confusing | Visual Studio's configuration matrix is known to puzzle people | It appears from two modules or two outputs; names are plain |
| Edits through a link | Two projects can write the same module | Edits go to the source, one writer, a banner |
| Large projects | A themed pack mixes very large modules | Modules load on demand; problems are cached per module |
| A combined resource that the game or a server mishandles | Nobody working on this repository can run GTA V ([Dlc_Pack_Creation.md](../features/Dlc_Pack_Creation.md)) | Compare plans with resources known to work; record "verified in game" per output kind, set only by a tester |
