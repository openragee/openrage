# GTA VI modding guide

What you can do with a GTA VI install in OpenRage today, in the order you would do it: give it your executable's keys, find files, open and extract them, edit one and save it as a file of its own, write a copy of an archive, and check what the copy changed. [File_Support.md](../features/File_Support.md#gta-vi) says which kinds of file read and write.

⚠ An archive OpenRage writes is one of two kinds, and neither has been run in the game: a rebuilt archive, whose table changed, is refused by the game because only the game's maker can sign a table, and a patched copy keeps the signed table byte for byte, so no check read in the game's code rejects it, but no run of the game was made with one ([the limit](#the-limit)).

## Give OpenRage your executable's keys

An archive's table of contents is enciphered, and the keys that decipher it are in the game's executable. OpenRage ships no key: it reads them out of your own executable — `game_scarlett_master.exe` of an Xbox Series build, `eboot.bin` of a PlayStation 5 one.

- `openrage-cli keys gta6 --exe <executable>` reads the keys from the executable of a build OpenRage knows, and refuses any other. It writes them as `gtavi_magic.dat` in OpenRage's configuration folder, masked so that the file opens only with that same executable, and it will not replace a file already there unless you pass `--force` or name another file with `--out`.
- The app unmasks the snapshot with the executable in the GTA VI folder set in Settings ▸ Games, and the CLI with the one `--exe <executable>` names; the environment variable `OPENRAGE_GTA6_EXE` names it for both. A masked snapshot is refused when no executable is given or it is another one.
- With an executable given and no snapshot file found, the masked snapshot OpenRage carries opens with it, or the keys of a build OpenRage knows are read out of it, and either is kept masked in the configuration folder, so the first step can be skipped.
- `OPENRAGE_GTA6_KEYS` names a snapshot file elsewhere, and every `openrage-cli rpf9` verb takes `--keys <file>` for one run, with `--exe <executable>` for a masked one.

The snapshot holds three kinds of key: the table key, the content key that deciphers an enciphered entry, and the string key that deciphers a metadata document's strings. A step below that needs one says so when it is missing.

## Find files

With the keys, a GTA VI install is browsed exactly as a GTA V one is: one Files tree, in which an archive is a folder, a nested archive is a folder inside it, and a double-click opens a file. There is no separate archive panel.

- **In the app.** Open the install folder. Each archive opens in the Files tree from its deciphered table: a folder for each folder its names make, an entry no name resolves under its hash, and a nested archive as a folder of its own. The filter finds a row by its name, its kind or its hash in the `0x` form Copy hash gives. The Inspector shows a selected entry's kind, its stored and real sizes, whether it is enciphered, the shape of its row and, where no name is held, its name hash.
- **In the CLI.** `openrage-cli rpf9 list <archive> [inner/path]` prints an archive's entries, with `--nested` one level of nested archives too, `--groups` the table's columns and `--json` one JSON document. The inner path walks into nested archives, and a component or an `--entry` names an entry by its name, by its hash as `0x…` or `hash_…`, or by its number. `openrage-cli rpf9 find <folder>` finds entries across every archive of an install, nested ones included, by `--name`, `--hash` or `--kind`, and `openrage-cli rpf9 census <folder> --out <folder>` writes the counts of entries, nested archives and enciphered entries per archive, never an entry's name, as a Markdown table.
- **With no key, a scan.** Without the keys, or where a table does not open with the keys held, an archive is listed by a scan of the bodies it stores in the clear, in a tab of its own, and a message says why. Only then does the install folder's view show a bar that says why no table opened, with Scan every archive, which tallies each archive's bodies by kind and finds one by archive, offset or kind, and Harvest names. A scan finds no enciphered body, and it addresses a body by its offset, not its name.

### Names

A row names its entry only by the 64-bit hash of its path. OpenRage shows a name where it holds a text that hashes to it, and the hash otherwise. No list of the game's paths ships with OpenRage. The names come from these places, and where two give one hash a name, your own names win:

- **Your names folder**: the one `--names <folder>` names for a CLI run, or otherwise `OPENRAGE_GTA6_NAMES`, for the app and the CLI. It may hold `resolved-names.tsv`, whose rows are `0xHASH<TAB>name`, the tables of a recovered-names folder, and `vocabulary.txt`, one name a line.
- **What you mined and harvested**, kept in the `gta6_names` folder of the configuration folder. `openrage-cli hashes mine <install> --out <file>` tries the strings the install's bodies state, those of your executable (the one `--exe` or `OPENRAGE_GTA6_EXE` names, else the one in the install folder) and, with `--listings`, those of lifted script listings, against the hashes no name resolves, then rules over the names already resolved, and keeps a candidate only where it hashes to one. It writes what it finds to the file `--out` names as `0xHASH<TAB>name` rows, after each archive as it goes and keeping the rows already in it, so a run that is stopped keeps what it found, and it merges every 64-bit name it found into `resolved-names.tsv` in that `gta6_names` folder without replacing a name already there, which the tree reads, so its names show without `--out` naming a file there; its 32-bit structure and member names go to the file of that folder the metadata reader loads. The same folder holds the vocabulary that Harvest names, the Harvest GTA VI names command and `openrage-cli rpf scan-names` keep from the names the bodies spell. Listing or opening an archive never writes either, and none of it is written into the repository.
- **The miner's ceiling.** Each of the miner's two walks over an install, one reading bodies for their schemas and one for their strings, reads at most `--max-bodies` bodies of each archive, 50,000 unless you give another number or `unlimited`, so that every archive is sampled, and `--max-total` bounds the whole install. Its report gives a line per archive with the bodies each walk read and the names found, marks an archive that stopped at the ceiling, and says how many stopped; `--archive <n>` reads the bodies of only the n-th archive the report numbers, under the same ceiling, and repeats; every other archive still gives its table's unnamed rows as targets, so an archive marked as stopped is read again on its own with a larger `--max-bodies`.
- **The cache.** Your names folder and that `gta6_names` folder are read through one cache file in the configuration folder: `gtavi_names_cache.dat` with no names folder, and with one a file beside it named by a digest of the files read, so another names folder keeps a cache of its own. A cache is keyed by the path, size and modification time of every file it was read from, so a run after the first reads that one file while its sources stand, and a source that changed, or a cache copied to another configuration folder, rebuilds it. On one build's names folder of 3,830,017 names, a load with no cache kept took 5.52 s and one from the cache 490 ms (`the_names_load_warm_from_the_cache_faster_than_cold`, on 2026-11-26 at `ab3a0cf2`, in the optimized test profile beside five other install-gated tests); in the app, the first archive of a run opened in 5.8 s with no cache kept and in 1.0 to 1.6 s with one, timed by hand on the same day.
- **In the app, the names OpenRage holds with no game data**: those of the installed schema snapshot, the public names and the parser names, each under its path hash.
- **The bundled words**, last: plain words shared across titles and hash functions, in the data files of `or-io`, with no hash column, no build-specific path and no game file extension.

The app builds its names once a run, on a worker, before an archive asks for them. Missing names still show as hashes.

## Open and extract

- **In the app.** In the Files tree, a double-click on an entry opens it, and a single click opens it in the preview tab. A body stored in the clear opens in the view its kind has. An enciphered body is deciphered on a worker with the content key: a PSO or RBF opens in the metadata editor, text as text, a resource in the view a clear one of its kind shows, and anything else as its bytes. Extract writes a row's body as the open reads it.
- **A metadata document's strings.** A PSO document's enciphered strings are deciphered with the string key and name the hash values the document holds; without it the document opens and says that the names need the key snapshot.
- **In the CLI.** `openrage-cli rpf9 extract <archive> <folder> [inner/path]` writes each entry's body, inflated, under its name or its hash, or only the one `--entry` names or those whose name holds `--filter <text>`. An enciphered entry is written only with `--decrypt`, deciphered first; a nested archive is written as the bytes its row states, an archive that opens on its own.
- **By scanning, with no key.** `openrage-cli rpf extract` writes the bodies a scan finds, or those of one family with `--kind`, and with `--as converted` writes textures as PNG, models as glTF, metadata as XML and audio as Ogg Opus; `openrage-cli rpf scan-body` writes one body, as it is stored with `--stored`, a metadata body's XML with `--xml` or a text table as GTA V's text table with `--gxt2`.
- **Scripts.** `openrage-cli script compiled <body>` reads a deciphered script body, which `rpf9 extract --decrypt` writes, as a compiled program: its header, its instructions and its native calls, with `--listing` every instruction at its code offset, and with `--natives` each call's native by its address in the executable, never by a name. `openrage-cli script decompile <body>` writes the same body as source, and `script export` every program of an archive or a folder, with names only from the lists you supply ([GTA_VI_Script_Decompiler.md](../features/GTA_VI_Script_Decompiler.md)). [A script's values](#a-scripts-values) says how one is edited.

## Edit and save a file of your own

A body opened from an archive is never written into the archive file it was read from, and a save over that file is refused. Save puts a document opened from a row of an archive's own tree into that row of the tree, which the archive's Save as… then writes to a new file ([below](#an-edit-in-the-app-from-the-files-tree-to-a-patched-copy)).

- **Save As** writes the body, with the edits its view takes, as a file of its own. A name ending in `.xml` writes a metadata body's XML and one ending in `.gxt2` a text table as GTA V's text table; a resource saves as a loose resource, which OpenRage opens again on its own. A view holding edits that no writer takes refuses Save As rather than drop them.
- **Checksums.** A GTA VI `zppp` PSO's `CHKS` is computed again on save. A frame whose rule OpenRage does not reproduce keeps the checksum it was read with, and the save of an edited one warns that the game may refuse the file for it.
- **In the CLI.** `openrage-cli rpf scan-from-xml` writes an edited XML back into a headerless metadata body as a loose resource, and `openrage-cli ttpf replace` writes a texture pack with one texture replaced from an image, to the file `-o` names.

Which values of a model, a bound, a map or a metadata body can be edited is in [File_Support.md](../features/File_Support.md#gta-vi), and a refusal names what it cannot write.

## Write a copy of an archive

Every write goes to a new file: the source archive is only read, the file named for the copy must not exist yet, and a write that fails leaves no partial file behind. Each write says which of the two kinds it wrote.

- **A patched copy** puts each changed body in its entry's place, chunk by chunk, and keeps every header, table and signature byte as the source holds it. The table's signature still matches and no check read in the game's code rejects such a copy, but no run of the game was made with one, so whether the game loads it is not known.
- **A rebuilt archive** has rows added, removed, renamed or resized, or its table laid out again. The game checks a signature over the table when it mounts an archive and only its maker can sign one, so the game refuses a rebuilt archive.

A body goes into a patched copy only at the length its row stores, and each changed chunk only where its new DEFLATE stream fits the stored size the signed table gives that chunk. So the edit has to keep the body's length: a value changed in place, not a text lengthened or a row added.

### An edit in the app, from the Files tree to a patched copy

The path below opens one row, edits it, saves it into its row and saves the archive as a new file, all in the app, and then checks the copy against its source with the CLI; [the same in the CLI](#a-patched-copy-step-by-step) follows it. It works the same for every row whose view saves its edits: a text table, a metadata body, a model, a texture dictionary, a clip and the other kinds whose edits [GTA_VI_Builds.md](../features/GTA_VI_Builds.md#what-is-read) lists, a headerless resource as well as any other row.

1. **Find the row.** With the keys held, the install folder's Files tree shows each archive as a folder and a nested archive as a folder inside it; `openrage-cli rpf9 find` finds the archive that holds a name too. Open that archive on its own with File ▸ Open file…, since a GTA VI archive is saved only from a tree of its own. Type part of the row's name, its kind or its hash in the `0x` form Copy hash gives into the filter, and select the row: the Inspector shows its kind, its stored and real sizes and whether it is enciphered.
2. **Open it.** Double-click the row. It opens in the view of its kind, deciphered on a worker first where its row is enciphered: a PSO or RBF body in the metadata editor, a text table as its texts, a model in the viewport.
3. **Edit it, keeping its length.** What keeps a body's length, and so can be patched, is an edit that moves nothing: a number or a flag changed, a text replaced by one of the same length, a vertex moved, a texture re-encoded at its own size, format and mips, a clip's key changed within its block. A text table is written over its own section, and an edit that changes a block's size writes the table anew, with a message that the archive will then be rebuilt. A metadata body read from XML changes only the bytes of the value edited, so a value of the same length keeps the length, and after a form edit its Text view shows that text, the source with the value changed; an element added, removed or moved writes the document again from its fields, and the tree's Save as… then names the row and why it keeps the copy from being patched. A clip key edit that grows its block says at once, in a warning, that the clip's length changes and its archive will be rebuilt. A text made longer, an item added or an item removed changes the body's length, and the archive then saves as a rebuilt archive.
4. **Save it into its row.** Save writes the document's edits into the row it was read from, in the tree only, on a worker: the message says that the document is saved into its row of the archive and that the archive's Save as… writes it to a new file, the row shows as edited, and no file is written yet. Where a PSO's checksum is kept as it was read, a warning says that the game may refuse the file for it.
5. **Save the archive.** File ▸ Save as… of the tree plans the save on a worker, then says which copy it writes before asking where. When every changed body keeps the length its row stores and fits its entry's chunks, the question is titled "Save a patched copy" and says that the edits save as a patched copy. Otherwise it is titled "Save a rebuilt archive", says "save as a rebuilt archive, which the game refuses because only its maker can sign the table", and follows with "These rows keep it from being patched in place:" and each row with its reason, as [A rebuilt archive](#a-rebuilt-archive) lists them. With nothing edited, the question is titled "Save a copy", and the copy is the archive as it was read, byte for byte. The dialog then asks for a new file, offering the archive's name with `_edited`; the archive read is never written, and a file already at the name picked is refused.
6. **Read what it wrote.** The message after the save says it again of the file written: that it "is a patched copy", whose table is byte-identical, so the table's signature still matches and no check read in the game's code rejects it, and that the game has not been run with it; that it "is the archive as it was read"; or that it is a new archive whose table changed, which the game refuses because only its maker can sign the table, with the rows that kept it from being patched.
7. **Check the copy against its source.** `openrage-cli rpf9 verify-patch <archive.rpf> <copy.rpf>` reads both with your keys, writes nothing, and holds the copy to what a patched copy is: the same length as its source, every header, table and names span of every archive in it, nested ones included, byte-identical, every byte that differs inside the stored body of a row, and each such row reading through its table at the size its table states, deciphered where it is enciphered. It prints each changed row by its name or hash with the bytes that differ, stored and inflated, and ends with one line: a patched copy, or not one and why, naming the span that differs or the row that does not read. It exits with success only for a patched copy.

File ▸ Save into a copy of the archive… saves the document's edits into a new copy of the archive it was read from in one go. With nothing edited it says so and asks nothing; otherwise it asks where, under the title "Save a copy", builds the body on a worker, and says after the write which copy it is with the same sentences as the tree's Save as…: a patched copy, the archive as it was read, or a rebuilt archive with the rows that kept it from being patched.

### How the path was checked on a build

On 2026-11-26 the path above was driven through the app on one Xbox build, a step at a time by a script with no window, with the app built from the code `ab3a0cf2` holds, and each copy was compared with its source by a script outside the tree, the comparison step 7 makes. No run of the game was made with any copy, so whether the game loads one is not known. What the copies showed:

- **Three edits, three patched copies.** A text of a text table replaced by one of the same length, a value of a metadata XML replaced by one of the same length, and a number of a headerless metadata body raised by one were each saved into their row, and the tree's Save as… asked "Save a patched copy" and said after the write that the file is a patched copy. Each copy reopened in OpenRage with its edit.
- **Each copy against its source.** Each copy is the size of its source, and the bytes that differ lie in one range inside the edited row's stored body: 459, 500 and 1,758 bytes. Not one byte of a table span differs, of the 42 the larger archive holds, its top table and every nested one, nor of the smaller archive's one. Inflated, each body differs from its source only in the edited value: 3 bytes, 4 bytes and 1 byte. A changed chunk's new stream differs nearly whole from the old one, and an enciphered row's is enciphered again over the whole chunk.
- **What was refused, and said.** A text made longer planned "Save a rebuilt archive" and named its row, 32 bytes over the length its table states. A value of the same length can still miss: the first value tried in the metadata XML deflated 2 bytes over its chunk's stored size, and of five values of that length tried for it, one fitted.

### A patched copy, step by step

This is the CLI's path: the one for a script's values, which the app does not edit, for a body edited outside OpenRage, and for a chunk past the app's cap ([what fits today](#what-fits-today)). Below, `<entry>` names an entry of `<archive.rpf>` by its name, its hash or its number, and `<path>` is that same `<entry>`; for an entry of a nested archive, step 1 gives the nested archive's path as `[inner/path]`, and `<path>` is that inner path, a slash and the entry. `openrage-cli rpf9 find <install> --name <text>` prints, for each entry whose name holds the text, its archive, the inner path of the nested archives above it and the entry itself.

1. Extract the body: `openrage-cli rpf9 extract <archive.rpf> <folder> [inner/path] --entry <entry> --decrypt`. It is written inflated and, where its row is enciphered, deciphered.
2. Edit that file without changing its length.
3. Ask whether it fits, which writes nothing: `openrage-cli rpf9 fits <archive.rpf> --entry <path> --with <edited file>`. It prints, for each chunk, whether it is unchanged and keeps its stored bytes, or how many bytes its new stream takes under its ceiling and how many are to spare; a body that does not fit is named with the reason, its length or the chunk that outgrows its ceiling, and the command exits with failure.
4. Write the copy: `openrage-cli rpf9 patch <archive.rpf> --entry <path> --with <edited file> --out <new.rpf>`. It says how many chunks changed and how many bytes it wrote, and that the copy is a patched copy. A row it cannot put in place is refused by name and nothing is written; `rpf9 replace` would rebuild the archive instead, which the game refuses.
5. Check what it wrote: `openrage-cli rpf9 verify-patch <archive.rpf> <new.rpf>`, as [step 7 of the app's path](#an-edit-in-the-app-from-the-files-tree-to-a-patched-copy) says.

`--entry` and `--with` repeat in pairs, one pair a row, and both verbs take `--names`, `--keys` and `--exe` as the other `rpf9` verbs do. An enciphered row is enciphered again where it lies, and a nested archive itself is refused: patch the entries inside it.

A mod of many rows is a folder. `openrage-cli rpf9 fits <archive.rpf> --from <folder>` and `openrage-cli rpf9 patch <archive.rpf> --from <folder> --out <new.rpf>` take each file under the folder as the new body of the row at its path, a nested archive's rows in a folder of the nested archive's path. `rpf9 extract` of a whole archive writes a nested archive as one file, which `--from` takes only unchanged; to edit rows inside it, delete that file and extract its rows into a folder of its path with `openrage-cli rpf9 extract <archive.rpf> <folder>/<inner/path> <inner/path>`. A patch adds no row, so a file whose path names no row refuses the whole folder by that file's name, and nothing is written; a nested archive given whole is taken only unchanged. Every row is planned before anything is written, and both verbs print a line a row: that it fits and what it would write, or why it does not, with its bytes. `patch` writes the copy only when every row fits; with `--skip-unfit` it patches those that fit and lists the others. Put in the folder only the files you edited: every file in it is planned.

### A script's values

A compiled script is edited by the values its pushes push, never by its code, and only in the CLI. What the edit writes is a script body of the source's length, not an archive.

1. Extract the deciphered body: `openrage-cli rpf9 extract <archive.rpf> <folder> [inner/path] --entry <entry> --decrypt`.
2. Find the push to change: `openrage-cli script compiled <body> --listing` prints every instruction by function, at its code offset.
3. Write the edited body: `openrage-cli script compiled <body> --set-int <offset>=<value> --set-float <offset>=<value> --out <new body>`. Each `--set-int` sets the integer the push at that code offset pushes, and each `--set-float` the 32-bit float a 4-byte push pushes; the flags repeat, an offset or an integer may be written in `0x` hex, and every other byte of the body is written as it was read. The new file must not exist yet.
4. Put the body into a patched copy with `rpf9 fits`, then `rpf9 patch`, [as above](#a-patched-copy-step-by-step).

Refused by name, and nothing written: an offset at which no instruction starts, a branch, whose operand is a code position, an instruction that is not a push of one immediate value, an integer the push's immediate cannot hold, and a float for a push that is not 4 bytes. `--set-string` is refused: every string constant of the build's compiled programs names one same object, so no string text was found to replace. No run of the game was made with an edited program, so whether the game runs one is not known.

### What fits today

The patch writer deflates a changed chunk with each of zlib's levels and, where none fits its stored size, with an optimal parse (zopfli), but only on a chunk no larger inflated than `OPTIMAL_CAP` in `crates/io/or-io/src/container/rpf/gta6_patch.rs`, because the parse's time grows with the chunk; it runs over a chunk in parts of 64 KiB, each with the 32 KiB before it as its window, and a larger chunk's refusal names the cap and says that the optimal parse was not tried on it. That cap is what `rpf9 fits` and `rpf9 patch` use; a save from the app runs the parse only on chunks of up to 256 KiB, since the app's plan does not yet report its progress or stop, and the parse takes minutes over a chunk of several MiB. A stream shorter than its stored size is filled with empty blocks or followed by zeros, which the reader and the game pass over. What fits:

- a chunk the edit leaves alone, whose stored bytes are kept as they are;
- a chunk the game stored without compression, which takes any content of its exact length;
- a changed chunk whose new content deflates within its stored size at one of zlib's levels, or, within the cap, under the optimal parse, which `rpf9 fits` tells you before anything is written.

The figures below were measured on 2026-11-26 on one Xbox build, on the code `ab3a0cf2` holds unless a line names another, and say what fits that build's signed tables, not what the game loads; no run of the game was made with any copy they describe:

- **Unchanged chunks deflated again.** `gta6_edits_that_fit_in_place` samples up to 40 deflated chunks a kind, in bodies stored at no more than 4 MiB, deflates each one's own content again and runs the optimal parse on those of 256 KiB or less within a time budget that gives each kind an equal share: 435 of 443 chunks fitted within their stored size with the optimal parse, against 21 with zlib's best level. That sample held no height-map body, and the suite now fails a kind it finds no body of. No sampled deflated chunk was larger than 8 MiB, which, as the sample leaves out every body stored above 4 MiB, is not a count of the build. The game's compressor packs tighter than zlib: on a wider sample of 1,613 bodies of ten kinds, read on 2026-11-25 at `57eece64` by a script outside the tree at zlib's level 9, 42 of 3,249 deflated chunks fitted, and zlib's stream was between about 1 % and 11 % larger than the game's, by kind. The suite asserts that zlib fits fewer than one deflated chunk in twenty and prints the optimal parse's counts.
- **An edit made by each writer.** `gta6_edit_to_patched_copy` makes one edit of a real row of each kind with the writer OpenRage edits that kind with, plans it with the patch writer at `OPTIMAL_CAP`, and reads the copy back: a text table written over its own section, the same edit saved as the app saves a text table, a script's pushed value set with `script compiled --set-int`'s writer, a PSO of the table form, a PSO of the other form, a headerless metadata body, a texture dictionary with a texture re-encoded and a drawable with a vertex moved each fitted, every changed chunk by the optimal parse, and each read back as its edit. The same text edit written by the writer that lays the table out anew came out 16 bytes over its row's length and was refused. The suite fails on a kind with no row found.
- **A clip's key.** `single_key_edits_of_the_build_s_clips_that_fit_their_blocks` changes one key at a time in clips of the build: 121 of 132 single-key edits kept the clip's length, and the 11 others grew a block, so their archive saves rebuilt.
- **A one-byte edit.** `gta6_patch_in_place` changes one byte of sampled rows of each row shape and patches it in: 15 of 17 rows fitted, an enciphered 20-byte row among them, and the two others were refused by name, each a chunk whose new stream outgrew its stored size.
- **What a cap leaves out.** Counted on 2026-11-26 at `57eece64` by a script outside the tree from the chunk tables of every archive of the Xbox build 1.0.2.1, nested ones included, without inflating a body: 208,477 of the 2,243,921 deflated chunks (9.3 %) are larger than 256 KiB, the app's cap, and 205,452 of the 1,178,052 rows with a chunk table (17.4 %) hold at least one such chunk; past 1 MiB lie 74,667 of the chunks (3.3 %), in 74,526 of those rows (6.3 %); past 8 MiB, the CLI's cap, 1,886 (0.08 %), in 1,885 of them (0.16 %); and no chunk is larger than 32 MiB. A changed chunk past the cap fits only where a zlib level fits it, and zlib fits about one chunk in a hundred, so an edit of a row with a chunk past 256 KiB that does not fit from the app is worth asking `rpf9 fits` about.

These suites are install-gated: they skip without the keys and the build that `OPENRAGE_GTA6_KEYS` and `OPENRAGE_GTA6_BUILD` name, and a skip is not a pass.

### A rebuilt archive

From the app, a save is a rebuilt archive whenever one row keeps it from being patched, and the save's question ([step 5](#an-edit-in-the-app-from-the-files-tree-to-a-patched-copy)) and its message after the write name each such row with what kept it:

- **A row renamed, removed or added in the tree**: the row "is renamed", "is removed" or "is added", since each changes the signed table.
- **A body of another length**: the row is so many bytes, not the size its row states, and so many bytes over or short. A headerless resource states no real size, so its row is held to the length of the body it stores, and a loose form that does not read as a resource from its start is named for that.
- **A chunk that does not fit**: a chunk of the row deflates at best to so many bytes by the tree's deflater and by the optimal parse, and neither fits its stored size, so many bytes over; past the save's cap, the message says that the optimal parse was not tried on it.
- **A row the patch writer will not write in place**, by its refusal (`PatchRefusal` in `crates/io/or-io/src/container/rpf/gta6_patch.rs`): a nested archive itself, whose rows are patched instead; a row under a cipher OpenRage does not encipher; a row with no chunk table whose body is neither one stream nor one stored body that reads back the same; and a row whose table states no body or does not read.

A save is refused, and nothing is written, for an archive moved into the tree from another, which the GTA VI writer does not add. In the CLI, the verbs below lay a table out again, and each that rewrote a table says that its signature is stale and that the game refuses the archive.

- `openrage-cli rpf9 copy <archive> --out <new>` deciphers each table, enciphers it again and copies every body; a copy that changed nothing keeps every table and signature as it read them.
- `rpf9 replace` sets an entry's body from the file `--with` names, `rpf9 remove` drops an entry and `rpf9 rename` gives one the path `--name` names; each takes the inner path and the `--entry` selector `rpf9 list` takes, and an entry of a nested archive is written in the nested archive first, then in its parent's row. `rpf9 replace` names `rpf9 patch` where its change would have fitted in place.
- `rpf9 defrag` packs the bodies in order, `rpf9 add` adds an entry and `rpf9 build` makes an archive from a folder.

A replaced body is stored in the clear, so it loses its content cipher, and one that OpenRage's reader would not read back is refused. Refused by name too are a plain replace of an entry whose row describes a paged resource, which `rpf9 replace --resource` replaces by its loose form instead, a replace of a nested archive itself rather than of the entries inside it, and an edit of a table that, laid out again unedited, would not come out as it was read.

## The limit

The game verifies a signature over an archive's table of contents when it mounts the archive, and only the game's maker can sign one, so the game refuses every rebuilt archive: those of `rpf9 replace`, `remove`, `rename`, `defrag`, `add` and `build`, of `dlc create-gta6`, and of the app's saves when a change does not fit. A patched copy keeps the signed table byte for byte, and no check read in the game's code rejects it; no run of the game was made with one. OpenRage checks structure, that a written archive reopens, lists and reads back, and with `rpf9 verify-patch` that a patched copy differs from its source only inside the bodies of its rows, and claims nothing about the game loading it.
