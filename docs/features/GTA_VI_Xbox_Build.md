# GTA VI Xbox build

What OpenRage reads, edits and saves of a GTA VI Xbox build, what it refuses and why, and how far each part was checked against a real build.

GTA VI is a title of its own (`crates/title/or-title/src/game/profiles.rs`) with no declared format: nothing of it is a `#[record]` declaration, because there is no source to name a field by. Its readers are ordinary code in `crates/io/or-io/src/gta6/`, behind `or-io`'s `gta6` feature, and a name there says the role a field was measured to play. The archive is read from its table by `crates/io/or-io/src/container/rpf/gta6_rpf.rs` and the files beside it, and scanned where no key is held. The layouts themselves are in the gitignored docs/extra/ tier and are not repeated here.

## An archive is read from its table

An RPF9 archive's header is in the clear, and its table of contents is enciphered with keys that are in the game's executable. OpenRage ships no key: it reads them out of the user's own executable, and [GTA_VI_Modding.md](../guides/GTA_VI_Modding.md#give-openrage-your-executables-keys) gives the steps. With them, an archive opens behind `RpfArchive` as `RpfVersion::Rpf9` and is browsed as a GTA V archive is.

- **One Files tree.** An archive the app opens is a folder of the Files tree, a nested archive is a folder in it, and a double-click opens an entry (`src/state/rpf_archive_open.rs`). An entry is read through its row's chunk table (`crates/io/or-io/src/container/rpf/gta6_mount.rs`, `crates/io/or-io/src/container/rpf/gta6_chunk_table.rs`), and an enciphered one is deciphered on a worker with the content key (`crates/io/or-io/src/container/rpf/gta6_content.rs`).
- **Names.** A row names its entry by the 64-bit hash of its path. The tree shows the text where OpenRage holds a name that hashes to it, and the hash otherwise; the names are a folder of names `OPENRAGE_GTA6_NAMES` names, or with none named the folder a package ships beside the executable from `assets/gta6_names/vocabulary.txt`, the table `hashes mine` writes into the configuration folder and the harvest kept there ([below](#names-naming-rules-and-use-labels)), read into one cache there (`crates/io/or-io/src/container/rpf/gta6_name_cache.rs`), then, in the app, the names of the default hash index (the installed schema snapshot's, the public names and the parser names), each under its path hash, and last the bundled words, plain words in `or-io`'s data files with no path, hash or game file extension. [GTA_VI_Modding.md](../guides/GTA_VI_Modding.md#names) says where each is kept.
- **Kinds.** A row states what its entry is, a 24-byte row by its class byte and a 20-byte row by its resource type code (`crates/io/or-io/src/container/rpf/gta6_kinds.rs`). The tree and the Files table show each row's kind, and the filter matches a kind's words and the GTA V extension of the same kind. The Inspector shows a selected entry's kind, its stored and real sizes, whether it is enciphered, the shape of its row and, where no name is held, its name hash (`src/ui/panels/inspector/rpf9_entry.rs`).
- **The tree's actions.** A single click opens a row in the preview tab, read on the load worker as a double-click reads it, and Copy hash gives the 64-bit path hash the table states, in the `0x` form the filter finds a row by (`src/state/rpf9_tree_actions.rs`).
- **Extract and save from the tree.** Extract writes a row's body as the open reads it, a clear headerless resource in the loose form OpenRage reopens (`src/state/rpf9_tree_verbs.rs`). A document opened from a row of an archive opened on its own saves into that row, on a worker, as a GTA V entry's document saves into its archive (`src/state/rpf9_tree_bind.rs`). The tree's edits are never written into the archive they were read from: Save as… writes them to a new file, as [How an edit is saved](#how-an-edit-is-saved) says.

The install opens as a plain folder, its archives in it.

### With no key, a scan

Without keys, or where a table does not open with the keys held, an archive opens in a tab of its own as the list of what a scan finds, a slice at a time on a worker, and a message says why (`src/state/rpf9_table.rs`, `src/state/rpf9_scan.rs`). `crates/io/or-io/src/container/rpf/rpf9_scan.rs` passes over the file and finds the bodies stored in the clear by their own bytes.

- **A find has an offset and no name or path.** Every scan command and view addresses a body by its offset in its archive. A body's end is stated only where its bytes state it or where the measured rule has no exception.
- **A find has a kind and a family.** The kind is what the bytes are (a nested archive, a run of zlib chunks, a stored resource, a movie, an audio container, an effect container, and a few more); the family is the word a person filters by: models, dictionaries, collision, navigation, animations, metadata, text, audio, movies, shaders, archives, other and unknown.
- **A headerless resource has a role.** A resource with no header is placed in a family of layouts by the shape of its first words (`Rpf9Role`): a drawable, a fragment, a bound, a dictionary, a navigation cell, a particle effects list and the others the enum lists. A resource no layout places opens as its bytes, under the reason.
- **A whole scan is kept.** A scan that read an archive to its end is kept in the configuration folder (`src/state/rpf9_kept.rs`), and the archive is listed from it while its size and modification time stand.

Only while no key opens the tables does a bar above a GTA VI folder's Files view say why, and offer Harvest names, which reads the names the folder's archives spell, and Scan every archive, which tallies the bodies a scan finds by kind across the folder, a click opening one (`src/ui/panels/hierarchy/gta6_install.rs`, `src/state/gta6_install_scan.rs`). With the keys held the folder is the Files tree alone.

⚠ A scan is not the table. A body stored enciphered, or one whose bytes fit no detector, is not found, and a body a scan finds saves only as a file of its own, never into an archive.

It is drawn as its strands and the sheet over their roots; the strands the game grows between the guides are not drawn.

A ped catalogue is a headerless metadata body of two lists of kits. A kit of the first states the assets of one part of a ped, a state at a time: a drawable and its albedo, normal and material maps, each by the 64-bit hash of its name. A kit of the second names kits and a state of each. The reader finds a member by its name hash in the body's own table and leaves the members it does not follow in the generic tree.

A reader names what it does not read. Where the meaning of a field is not known, the reader keeps the field as it was read and the view shows it under its stored form or its hash; the module headers under `crates/io/or-io/src/gta6/headerless/` list those fields file by file.

## How an edit is saved

Nothing is written into the archive a body was read from: every save writes a new file, of one of three kinds, and each save says which it wrote.

- **A loose resource** is a file that a read at offset 0 returns as the sections it was written from (`crates/io/or-io/src/container/rpf/rpf9_write.rs`). Save As makes one from a body opened from an archive or found by a scan, and Save writes over a loose resource that was opened from disk (`src/state/gta6_resource_save.rs`).
- **A patched copy** of an archive has each changed body written in its entry's place, chunk by chunk, and every byte of every table, header and signature as it was read. The table's signature still matches, and no check read in the game's code rejects such a body; the game has not been run with one.
- **A rebuilt archive** has rows added, removed, renamed or resized, or its table laid out again (`crates/io/or-io/src/container/rpf/gta6_container_write.rs`). The game checks a signature over the table when it mounts an archive, and only its maker can sign one, so the game refuses a rebuilt archive.

### A patched copy

`crates/io/or-io/src/container/rpf/gta6_patch.rs` writes a patched copy (`plan_patch`, `write_patched_copy`). A body goes in place only at its row's real size, split at the row's own chunk boundaries, because each chunk's sizes are in the signed table:

- A chunk's inflated size does not change, and its stored size is a ceiling: the game's read stops at the end of a chunk's DEFLATE stream and reads nothing of the bytes after it, up to the stored size.
- A chunk whose content is unchanged keeps its stored bytes. A stored chunk takes new content of exactly its length. A deflated chunk takes new content of its inflated length whose DEFLATE fits the ceiling, filled to it by empty DEFLATE blocks laid before the stream, or, for a slack of 1 to 4 or 8 bytes, which no run of them fills, by zeros after it, which the reader and the game pass over.
- An enciphered row is enciphered again over the windows its framing covers, at their absolute offsets, so an unchanged byte keeps its enciphered form.
- A body of another length, and a chunk whose DEFLATE outgrows its ceiling, are refused by name with their sizes.
- No write may touch a header, a table or a names blob of any archive on the way to the row, or the header and table of any archive nested in one. The copy is written beside its name, checked span by span against the source, and renamed only then; a file already at that name is refused.

A changed chunk is deflated again with zlib's levels and, if none fits its ceiling, with an optimal parse (zopfli, `optimal_deflate` in `crates/io/or-io/src/container/rpf/gta6_patch.rs`), which is tried only on a chunk of at most the cap its plan is given, `OPTIMAL_CAP` bytes inflated for `plan_patch`; past it, a chunk fits only where a zlib level fits it, and its refusal names the cap and says the optimal parse was not tried. The parse takes a chunk in parts of 64 KiB, its time growing with the chunk's length, and `plan_patch_with` takes the cap and a callback told the bytes planned, which stops the plan after the part under way, with nothing written, when it answers no. How many fit on one build, and the share of chunks a cap leaves out, are in [GTA_VI_Modding.md](../guides/GTA_VI_Modding.md#what-fits-today), with the steps of `rpf9 fits` then `rpf9 patch`. A save plans once and writes from its plans (`plan_patch`, `write_planned_copy`).

In the app, Save as… of an archive's tree (`src/state/rpf9_tree_verbs.rs`) and File ▸ Save into a copy of the archive… of a document opened from one (`src/state/gta6_archive_save.rs`) choose on a worker, planning with a cap of 256 KiB: a patched copy when every changed row is a body of the length its row stores that fits its chunks, a headerless resource's loose form turned back into the body its row stores first, else a rebuilt archive, and then the message names each row that kept the copy from being patched in place and why, by how many bytes where a size is off. A document opened from a tree's row saves into that row, which then shows as edited, and the tree's Save as… plans first and says which copy it writes before its dialog asks where: a patched copy, a rebuilt archive with the rows that keep it from being patched, or, with nothing edited, the archive as it was read, byte for byte. A text table is written over its own section, and a metadata body read from XML changes only the bytes of the value edited, so an edit of a value at its length keeps the body's length; an XML edit that adds, removes or moves an element is written again from its fields, and the tree's Save as… names that row; a clip key edit that grows its block says at once that a rebuilt archive follows. [GTA_VI_Modding.md](../guides/GTA_VI_Modding.md#an-edit-in-the-app-from-the-files-tree-to-a-patched-copy) walks one edit through it. In the CLI, `rpf9 patch` writes a patched copy and `rpf9 fits` says, writing nothing, whether each chunk of a replacement fits and by how many bytes one does not, of rows named one by one or, with `--from`, of every file of a folder at its row's path, planned all before anything is written; `rpf9 verify-patch` holds a copy to its source, writing nothing: the same length, every header, table and names span of every archive on the way byte-identical, and every byte that differs inside a row's stored body, which reads at the size its table states; `rpf9 replace` writes a rebuilt archive, and says so and names `rpf9 patch` where its change would have fitted in place.

### A script's values

`crates/io/or-io/src/gta6/script/compiled_write.rs` writes a compiled script program back: `write_back` encodes every instruction again from its decoded opcode and operands and leaves every other byte as read, and `set_int` and `set_float` change only the operand bytes of one push, so the body keeps its length and can go into a patched copy. A branch, an instruction that is not a push of one immediate value, an integer its immediate cannot hold and a float for a push that is not 4 bytes are refused by name. `script compiled --set-int`, `--set-float` and `--out` write an edited body to a new file, and `--set-string` is refused, because every string constant of the build's compiled programs names one same object; [GTA_VI_Modding.md](../guides/GTA_VI_Modding.md#a-scripts-values) gives the steps. No run of the game was made with an edited program.

### An edit that moves nothing, and one that changes a length

Edits of a body come in two kinds, and the difference decides how much can go wrong. Only one that moves nothing can give a body of its row's real size, which a patched copy needs:

- **An edit that moves nothing** is written over the bytes its reader read: a constant, a texture key, a bone's transform, a key of a channel, a particle value, a texture in its own size, format and mips. The body is read again on the save's worker and the values shown are written in place.
- **An edit that changes a length** lays out part of a section anew: a material that gains a parameter, a bone renamed, a geometry that outgrows its buffer, a navigation polygon deleted, a dictionary texture resized. `crates/io/or-io/src/gta6/map_grow.rs` adds and removes a map's entities the same way, and no view or command offers it yet. `crates/io/or-io/src/container/rpf/rpf9_grow.rs` moves every pointer at or past the edit. What a pointer is comes from a typed reader, so a word that looks like a pointer and that no reader names refuses the edit.

A pack saves as a pack: every row of a texture left alone is carried as the file stores it, and a replaced texture is written as zlib rows of the sizes its entry states (`crates/io/or-io/src/gta6/ttpf_write.rs`). A texture given another size, format or mip count moves every texture after it (`crates/io/or-io/src/gta6/ttpf_relayout.rs`).

⚠ No written file has been run in the game. A loose resource, a saved pack and a patched copy open again in OpenRage as what was written, which is a round trip through one description and proves nothing about the game's reader.

## What is refused, and why

| Refused | Why |
|---|---|
| Reading an archive's table without the keys | the table is enciphered and OpenRage ships no key; the archive is scanned instead |
| Writing into the archive a body or a tree was read from | every save writes a new file, and the source is refused as its path |
| A rebuilt archive, by the game | the game checks a signature over the table when it mounts an archive, and only its maker can sign one |
| A body put in place at another length, or a chunk whose DEFLATE outgrows its stored size | a chunk's sizes are in the signed table, so the change needs a rebuilt archive |
| Recomputing the checksum of a PSO frame whose rule OpenRage does not reproduce | its algorithm is not known; such a PSO is saved with the checksum it was read with, and the app says the game may refuse it, while a `zppp` PSO's `CHKS` is computed again (`src/state/gta6_meta_save.rs`) |
| A script's string constant set to another text | every string constant of the build's compiled programs names one same object, so `script compiled --set-string` is refused |
| Writing a changed save record | its header holds a checksum of an unknown algorithm, so a record is read and never written |
| A packed copy of a save | its body is compressed or encrypted; it is refused by the title and slot its clear head states |
| A program the native front end cannot lower, or whose resources it cannot bind | each refusal has a name; a pass with a refused program is not drawn in Shaded ([below](#shaders)) |
| An edit that would renumber what another body names | a navigation polygon another cell links to, a map other maps name as parent: the other bodies are saved apart |
| An entity retyped to an archetype its map does not already name | the archetype word is a namespaced hash and the writer refuses one the body did not hold |

Three words are kept as read because no rule derives them: a clip block's hash, a geometry's content digest and a PSO's checksum. Whether the game checks them is not known.

## Textures, the coder and its tables

A pack is a header, a table of rows, a directory of textures and bodies of tiled texture memory. A texture is keyed by the 64-bit hash of its lower-cased name, and the pack does not hold the name.

A body is stored plainly, as zlib, or through **BCPack**, the console's entropy coder over BC blocks (`crates/io/or-io/src/gta6/bcpack.rs`). The coder's lanes of every mode decode. Turning a lane's symbols back into blocks needs tables that are constants of the coder and are in no stream: a preset of blocks for each mode, which a block near a body's start is a difference from, and the tables that say which indices a symbol names. The tree holds them as one file, `crates/io/or-io/data/bcpack-tables.bin`, which every pack reads through unless you keep a file of your own.

### The tables file

The coder's tables are published as one file of a fixed layout, which `crates/io/or-io/src/gta6/bcpack/supplied.rs` reads. A body of BC1, BC3, BC4, BC5, BC6H or BC7 blocks is rebuilt through the tree's file alone, in place of BC1's built-in tables and of any calibration, and the app offers no calibration. `openrage-cli ttpf tables <file>` keeps another such file in the configuration folder, once, for every pack of every install, and every pack then reads through that one. What this section says of supplied tables holds for the tree's file and for one you keep alike, and the screens word both as supplied.

- **OpenRage ships one such file and vouches for no value of it.** The tree holds the file and nothing computed from it, and whose the tables are is not known ([LICENSE-third-party.md](../../LICENSE-third-party.md)). A file of another length, with other entropy models than the coder's, or that names a BC7 block the lane rules here would not rebuild, is refused by what is wrong with it. A file that reads has a tables file's layout, which says nothing of its values: a kept file is "supplied", and no more.
- **A read counts what speaks against the tables.** For each texture `Decode` counts the blocks drawn through a value no table gives, and the BC6H and BC7 blocks no encoder writes: a BC6H end a difference takes out of its base's range, an anchor's index with its top bit set, and two ends of a BC7 subset that disagree on the p-bit they share. No table is fitted to these rules, and tables that are right leave no such block. A BC1, BC3, BC4 or BC5 block has no such rule.
- **`ttpf tables --check <folder>` holds what is kept to the packs of a folder.** It decodes every coded body once and counts those blocks by mode, then says how far the coded mips are from the plain mips beside them. What it found is kept beside the file, by mode, with the file's digest, so it stands for that file alone; a mode the check read no block of stands as an earlier check left it. Supplied tables that leave one such block are not this coder's tables: the command fails and says so, and so do `ttpf info`, `ttpf export`, the pack's list, the inspector and the texture view, for every texture read through them. A later check does not take that back: one of other packs, which finds nothing, leaves the file failed. The count said of a failure is one check's own, over the modes it failed, and of two checks that fail, that of the one that counted more; the count said to be held of a mode is that of the largest check of it.
- **A listing or an export that counts such a block fails the file for that pack.** `ttpf info` and `ttpf export` read every texture they were asked for before they word one, so a texture that read clean beside one that did not is not called exact either: both went through the same file. The count is kept beside the file, with the file's digest and the pack's key, which is its file's name and length. Every later read of that pack through that file then says the tables are not this coder's, in `ttpf info`, `ttpf export`, the pack's list, the inspector and the texture view, whatever a check of other packs has held; the app keeps the same count when a texture it shows counts such a block. Another pack reads as the checks left the file.
- **When a texture is called exact.** Never before it is read, never through a file a check has failed or a read of its own pack has counted a block against, and never where a body of it through the coder was not read. A BC6H or BC7 texture is, once none of its blocks speaks against the tables and a check has held the file's tables of its format to the blocks of a folder; before that it says "supplied tables, not checked", because one texture reads few of a preset's entries and a wrong entry it reads need not break a rule in it. A BC1 texture is, when every preset slot and quadrant symbol it reads has the same value in the file and in BC1's built-in tables; otherwise it says how many of its coded blocks read a value the two give differently. A BC3, BC4 or BC5 texture never is: no rule of those formats can show a wrong table and no second table is known, so it says "supplied tables, no rule checks this format", whatever a check has held. A texture with a block that speaks against the tables says how many disagree. `ttpf info` and `ttpf export` end with a line for a pack whose blocks disagree, and the inspector says under the word what it rests on, with the counts of the texture's own format.
- **What exact means, and what it does not.** No texture is stored both coded and plain, so no coded body can be held against its own plain blocks: exact never means that the blocks were compared with the pack's. For BC6H and BC7 it means that no rule a wrong table breaks was broken, in the texture or in the check. The rules see an entry of BC6H's and BC7's preset lists through the blocks that read it: whether it is in its place, a BC7 end's p-bit and an anchor's top bit. They do not see each end value of each slot, nor the place of an entry that few blocks read: a value one step off passes them, in every entry at once as in one, so a texture called exact can hold blocks that are a step off where the file is. For BC1 it means that two tables agree, and two tables can agree and both be wrong. What stands for the values is measurement on your own packs, which the check prints: how far the coded mips are from the plain mips beside them, against the same figure through a calibration fitted from the pixels alone, which read nothing of the file. `ttpf tables --check <folder> --probe` goes value by value: it moves each field of each preset slot, each preset index and each pixel of each index symbol one step down and one step up, and counts the values that then meet the plain mips better than both neighbours, as well, or worse, by how many coded levels read each. A plain mip is another picture and the blocks of one level are of one picture, so a value few levels read is not determined by it; and it moves the indices of the plain mips' own blocks the same way, which shows what the measure says of indices that are right. A probe reads a texture whole from disk, its plain mips too, so of a folder that holds more than 1,024 BC1 textures it reads one BC1 texture in eight.
- **What stays unread.** A preset entry of BC1, BC3, BC4 and BC5 also holds indices, which a body would read through lane 1; that lane is zero in every such body of the build, a body where it is not is refused, and no rule here reads those indices. How a BC7 entry's second index set reads is not measured, and a file with one is refused.

### Where no tables file reads: a calibration, which is an estimate

⚠ A pack always reads through a tables file, the tree's or one you keep, so nothing of this section is reached by `load_cache`: it says what BC1's built-in tables and `crates/io/or-io/src/gta6/bcpack/calibrate.rs` do for a caller that hands a pack no tables file.

- **BC1 decodes through its built-in tables, and is not called exact.** The tables come with the port of bcpack-rs, whose author fitted them, and nothing confirms them value for value. A BC1 texture read through them alone is said to rest on the built-in tables, in the list, the inspector, the texture view, `ttpf info` and an export, the app's as the command line's. With a tables file kept, BC1 reads through that file instead, and each read holds the file's BC1 tables against the built-in ones: a block whose chain of references starts at a preset slot the two give differently, or one of whose quadrants carries a symbol they give differently, is counted, and the texture says how many of its blocks read such a value. `ttpf tables --check` counts those blocks over a folder, and `--probe` says how far they are from the plain mips through each of the two tables. Where the two differ is computed from your own file at each read and is nowhere in the tree. One preset slot has no built-in value, and a body that reads it is treated as the modes below are.
- **A texture whose coded body was not read is not called exact.** A read stops at the first body that does not read and gives the levels above it. With no tables kept, a BC3, BC4, BC5, BC6H or BC7 texture whose top levels are stored plainly reads those levels and no other: it says that its plain levels were read and its coded levels were not, in the list, the inspector, the texture view, `ttpf info` and an export. With tables kept, a texture whose coded bodies read down to one that does not decode says that a coded body of it was not read, and that only the levels above that body were.
- **BC3, BC4, BC5, BC6H and BC7 decode through tables fitted on the user's machine.** No texture is stored both coded and plain, so `crates/io/or-io/src/gta6/bcpack/calibrate.rs` fits each table against the plain mip levels beside a coded one, over the packs of a folder, in passes. BC6H and BC7 each read two presets, of endpoints and of indices, which `crates/io/or-io/src/gta6/bcpack/bc6h_fit.rs` and `crates/io/or-io/src/gta6/bcpack/bptc_fit.rs` fit.
- **A texture whose plain levels are not one another averaged down gives no target.** A map filtered anew for each level is such a texture; its coded levels are drawn through what the other textures fit, and vote only what those left open, against the pixels across each block's edges.
- **A signed BC6H texture is drawn through the tables the unsigned textures fit.** No signed texture has a plain level beside a coded one, so a calibration reads one only for what needs no target: the range of its ends, read as signed, and the pixels across its blocks' edges. What checks its decode needs no pixel either: an encoder's difference never takes an end out of its base's range, and the blocks of a signed body kept to that through tables fitted without them.

**A calibrated texture is an estimate.** It is the picture the fitted tables give, not the picture the game decodes, and it can be wrong in any block drawn through a slot or symbol the fit did not solve. `Decode` counts both: the blocks rebuilt through fitted tables, and those of them drawn through an unsolved slot. The inspector, the Gallery, `ttpf info` and an export each say "calibrated" with that share, and a save never writes an estimate: it carries the coded bodies as the file stores them.

`openrage-cli ttpf calibrate <folder>` and the app's job (`src/state/gta6_bcpack_calibration.rs`) fit the tables and keep them in the configuration folder for the packs they read, under a name the packs' names and lengths give, so a game moved to another folder keeps its calibration. The app offers the calibration in a pack's list while the game has neither a calibration nor supplied tables, until it is done or declined. A run that is stopped or cut short keeps where it stood after each pass, and the next run of the same packs goes on from there. A slot is fitted only from the packs read, so the folder named should hold every pack of the game. The table the command prints says how far each mode's coded mips are from the plain mips beside them, in 8-bit steps and for BC6H in stops, which is the only measure of a fit there is. A pass reads each texture once, on up to 16 threads that each hold one texture; `--coverage` then decodes every coded body of the folder once and counts, by mode, the textures that read with nothing against them, as estimates, or not at all, which takes longer than the fit.

## Names, naming rules and use labels

An archive's table names an entry only by a hash, and a pack names no texture. Names come from what the bodies spell.

**The harvest.** `crates/io/or-io/src/gta6/names.rs` reads the start of each body for printable names: the names resources state of themselves and of each other, and plain ones. Each name is hashed both ways, 32-bit and 64-bit (`crates/io/or-io/src/gta6/hash.rs`), into a `Vocabulary` kept in the configuration folder. From then on a hash read anywhere is shown by its name, in the CLI and in the app. The harvest also keeps the name each drawable and fragment states of itself, by its offset, which a scan's list shows beside the row. `openrage-cli rpf scan-names` runs it, and the app runs it as a job (`src/state/gta6_names.rs`, `src/state/gta6_install_harvest.rs`).

**Map names.** A map body states its name as two hashes, and few bodies spell a map's name. The names of the maps that go with a named map follow from it: its occlusion and level-of-detail maps, its instance maps by range and detail, numbered from 0, and its area's imposter maps (`crates/io/or-io/src/gta6/map_names.rs`). As with a texture, a rule makes candidates and a candidate names a map only where it hashes to the 64-bit word a body states. `rpf scan-maps` ends with how many maps, archetypes and entities the kept names name and how many maps more the rules name, beside the same count from the names reversed, which is what chance gives; `--names` keeps the names the rules gave with the others.

**A list of names.** `rpf scan-names --names <file>` holds each line of a file the user supplies as a plain name of the vocabulary, so a hash it names is shown by it wherever the vocabulary is asked. No list of the game's names ships with OpenRage: the bundled words are plain words with no path or game file extension. ⚠ A list found by searching for hashes can hold a name that hashes right and is wrong, and a 32-bit hash two held names share names nothing.

**Member names.** A metadata body states its own layout and names nothing: a structure, a member, an enum and its values are hashes. `openrage-cli meta snapshot --par-tree <dump.json>` turns a parser dump, the JSON a viewer of the executable's reflection tables carries, into a schema snapshot of GTA V's format (`crates/io/or-io/src/meta/par_tree.rs`), kept beside GTA V's in the shared store and never in the tree. The editor and the CLI read it for its names alone, and only for a GTA VI body: the readers and writers of GTA VI's metadata hold `hash_index::title_names()` while they work, and a GTA V document is named as if the snapshot were not there, because the two games' hashes are unrelated. A GTA VI body opens with the names the dump has in the clear and `hash_XXXXXXXX` for the rest. ⚠ A snapshot holds no offset: a dump's layout is the executable's, and a body may state another, so the body's own table is what is read.

**The naming rules.** A texture's name follows from the name of the drawable that uses it: the drawable's stem, then a map kind, a level-of-detail token swapped, a numbered variant, the stem's first or last tokens, or a ped component's pattern (`Rule` in `crates/io/or-io/src/gta6/texture_names.rs`). The rules make candidates, and a candidate names a key only where it hashes to one, so a rule can miss and cannot name wrongly short of a hash collision. Nothing there is a list of names. A file of names the user picks is read the same way.

**The use label.** A texture no name is found for is still used: the harvest records, for each texture key a model's material binds, the first model that binds it, the shader parameter that binds it there, and how many models bind it. The label is that model and parameter, as in "used by a model as its diffuse texture, and by two models more". It is not a name, since it hashes to no key; it tells a person what a nameless texture is for, and the pack's list filters by it.

## Shaders

GTA VI's Xbox programs ship as native GPU code with no bitcode. Two front ends in `or-shader-front` turn a program into naga IR, and neither runs the game's compiler:

- `dxil` reads a container that holds bitcode.
- `rdna` reads native code: `crates/tools/or-shader-front/src/rdna/decode.rs` decodes the instruction words, `crates/tools/or-shader-front/src/rdna/cfg.rs` cuts them into a control-flow graph, `crates/tools/or-shader-front/src/rdna/sym.rs` follows where each scalar register's value came from, which is the only way a program names its resources, and `crates/tools/or-shader-front/src/rdna/to_naga.rs` lowers a pixel, vertex, mesh or compute program to a module. Everything it does not model is refused by name (`NotTranslated`).
- `crates/tools/or-shader-front/src/rdna_bind/mod.rs` joins each resource of a translated module to the binding record its package lists and to the name the effect container's table gives that register, and refuses, by name (`Unbound`), a program the renderer has nothing to give: one that fetches its vertices from buffers the game fills, reads numbers the game passes with each draw, or picks a resource by a number the game sets.

The app translates the vertex and pixel programs a drawable's effects run, on a worker, once a session, into a pack held in memory (`src/state/gta6_shaders.rs`), and Shaded draws a pass only when both its programs translate and bind (`src/render/gta6_shaded.rs`). The Shaded button says how many programs of the drawable's passes are refused and why the first is. The other shading modes need no program.

The light of Shaded follows the install where its common archive is found: `src/state/gta6_timecycle.rs` reads the time table and the weather cycles among that archive's XML bodies with GTA V's reader, and `src/render/viewport/gta6_day.rs` puts the sun and the moon where the hour puts them, lets one of them light as their heights say, and takes the two samples of the weather's cycle that stand for the sun's angle. The cycle states the light's illuminance, its fade, its colour and what multiplies the sky's ambient; the Shaded line says when a model is lit this way. ⚠ Two things are still the editor's own: the exposure, which the game meters from each frame on the GPU, stands as one constant for sunlight and one for moonlight, and the colour of the sky and of the ground is the built-in sky's, since the game computes it from its atmosphere.

The sun's shadow on a GTA VI model in Shaded is the model's own, cast into one tile fitted to it by the mesh stages its programs draw with (`or_renderer::game_shaders::meshlets`). ⚠ What that shadow is today: every surface those programs draw casts whole, so an alpha-tested surface (leaves, a fence, hair cards) casts the shadow of its whole geometry, holes included, because the pass that casts runs a surface's mesh stage and no pixel stage; a surface drawn as Material beside the others casts none; and a model one of whose surfaces reads the view at an offset the light's view cannot be copied to casts none at all, which the Shaded line then says. The filter's arithmetic is the game's as read, and the turn of its spiral, how far it searches, the bias, the nearest-texel taps and the outermost tap's weight of nought are the editor's.

Shaded for a GTA VI drawable is therefore partial by construction: `rpf scan-rdna` and `rpf scan-rdna-bind` count, for an effect container, how many programs decode, translate and bind, and what stopped the rest, and [what a build's programs come to](#what-a-builds-programs-come-to) is what they counted on one build.

What a translated program is on a device is checked by `or-shader-tool rdna-devices` (the `device-check` feature), which builds every program and every pass's pair of a container into a pipeline on each adapter of the machine, in worker processes a driver's crash ends one of. `--draw` then draws with each pipeline, a stand-in at every binding and no vertex, so the device checks the pipeline against all it is drawn with and runs none of it: fed stand-ins, a program's loops need not end. `--software`, or `OPENRAGE_SOFTWARE_ADAPTER=1`, opens the machine's software adapter (Direct3D 12's Microsoft Basic Render Driver on Windows) and no other, so nothing of the check reaches a hardware driver; `--run`, which implies it, draws three vertices as points or dispatches one group with each pipeline, so the program runs on stand-ins that hold noughts, and an adapter that is no CPU's is skipped by name. A step that says nothing for `--timeout` seconds is ended and counted as timed out, one that ends its process twice as crashed, and with `--chunk 1` each unit runs in a process of its own. `--pick FILE` checks the units whose numbers the file lists, and `--list` prints every unit with a program's kind and entry name or the effects and techniques whose passes draw with a pair. `--msl` has naga write each stage as Metal's language with no device, with the checks and the resource numbers wgpu's Metal backend gives it; it refuses a stage that binds more buffers, textures or samplers than Metal gives a stage, and a pipeline whose vertex stage binds more buffers than that backend gives a pipeline's vertex stage, its buffer of sizes and its vertex buffers among them (`a_vertex_stage_is_held_to_the_sixteen_buffers_wgpu_s_metal_backend_gives_a_pipeline_s`). `--fit` writes each unit once more with its buffers brought within those counts (`rdna_bind::budget`), `--fed` checks each pair as the binder hands it to the renderer, and `--msl-dir DIR` keeps each stage's text for a Mac's own compiler. `rdna-devices --help` says how another machine adds its adapters to the report. What a reader may rely on:

- **Vulkan and Direct3D with DXC are the two backends the translated passes are built and drawn with in the app.** A Metal device builds them too, as [the check measured](#what-a-builds-programs-come-to) on one Mac; no frame of a model has been compared there.
- **Direct3D needs DXC.** FXC refuses programs that are valid (a gradient inside a loop, a barrier in a branch) and has no 64-bit integers. `or_renderer::instance` gives every instance the `dxcompiler.dll` beside the program, else one on `PATH`, else a Windows SDK's, and warns when it falls back to FXC; the app then says so once a run, in a notice that stays until it is clicked: the toast is short enough to show whole, and its Details button brings the Log forward, which holds what FXC loses and the two ways out (`the_notice_of_fxc_shows_whole_in_a_toast_in_every_language`). ⚠ A package for Windows ships neither `dxcompiler.dll` nor `dxil.dll`, so a machine with no Windows SDK compiles with FXC until a person puts the two files beside the program or starts it with `WGPU_BACKEND=vulkan`.
- **A pass that updates a texture of 64-bit texels is not built on Direct3D**: wgpu offers the feature there and refuses the texture, which `instance::updates_64_bit_textures` asks the adapter about.
- **OpenGL is not supported**: the shading passes index a table of textures at a computed place, which it cannot.
- ⚠ **One integrated adapter's Direct3D driver ends the process on some large mesh passes.** They are the passes whose mesh stage holds a loop inside a loop. The app opens such a card under Vulkan where Vulkan lists it; under Direct3D the builder of a pass refuses such a stage (`or_renderer::instance::refused_by_driver`) and its surface draws as Material with the reason. The check counts such a unit as skipped on that adapter, and `--try-refused` puts it to the driver all the same, to see whether the driver still ends the worker.
- A compute program is built and never run by the editor; the check runs one only with `--run`, a group on the software adapter.

|---|---|---|---|
| mesh | 9,282 | 9,277 | 5 write the memory a group's threads share |
| pixel | 12,101 | 12,091 | 10 are shaded in primitive order |
| vertex | 2,431 | 2,431 | |
| geometry | 195 | 195 | |
| compute | 2,689 | 2,622 | 64 trace rays, one updates a texel by compare and swap, 2 ran past the ten seconds a block is given |

**Almost no pass binds as it stands, and the reason is never the translator.** `openrage-cli rpf scan-rdna-bind <shaders.rpf> <offset>` over both: of 22,010 passes of a vertex or mesh program and a pixel program, 21,991 translate in both stages and 20 bind. The first stage reads a buffer the game fills when it runs in 17,628, takes no vertex attribute in 3,498, reads its descriptors' own words in 292 and numbers passed with each draw in 145; the pixel stage reads such numbers in 391, a buffer the game fills in 13 and a resource picked by a number the game sets in 4; 19 hold a program that does not translate.

**As the app translates them**, the count is by stage over a sample of drawables. `cargo nextest run --profile all -p or-cli --test gta6_shaded_stage_census --no-capture`, with `OPENRAGE_GTA6_BUILD` naming the build, sampled 1,385 drawables, every fourth model body of the archives it reached in its four minutes, which name 91 effects, and translated the passes of the 76 it reached in its budget: 163 of their 240 pixel stages, 75 of the others picking a resource by a number the game sets and 2 looping up to a number only the game fills, and 242 of their 350 mesh stages, of which 84 were not tried because the pass's pixel stage is refused, 12 place instances by a record only the game fills, 4 pick a resource, 4 read vertices a compute pass of the game's skins first, 3 loop and one writes shared memory. The share by the fallback's families is not counted: a family is read from a model's material and not from a program, and no measure joins the two.

**A Metal device builds those passes.** `or-shader-tool rdna-devices <shaders.rpf> <offset> --technique deferred_drawmeshlets,deferredalphaclip_drawmeshlets --draw --fed --msl --fit`, which opens the adapter with no surface: of the 748 pairs of the two techniques the binder hands the renderer 476, and the Metal device creates a pipeline of 413 of them and draws with each. It refuses 63: 52 whose vertex stage binds more buffers than wgpu's Metal backend gives a pipeline's vertex stage (`--fit` writes all 476 within the count, as text no device has built), 10 whose pixel stage Metal's compiler rejects (`no matching constructor for initialization of 'metal::gradient2d'`, on a line that samples one texture of an array by gradients), and one whose compile the system's compiler service dropped. The 272 not handed over are the binder's own refusals: 124 place instances by records only the game fills, 81 pick a resource by a number the game sets, 55 loop up to a number only the game fills, 10 are too large to have been checked on a software adapter, and 2 write targets whose contents are not established. Every one of the small container's 2,906 units, its 1,699 programs and 1,207 pairs, is created and drawn on the same device. The renderer's own builder of such a pass holds there too, over stages built by hand: the 44 tests of `game_shaders::meshlets` pass on that device (`cargo nextest run -p or-renderer --features gpu-tests --profile all --lib -E 'test(/meshlets/)'`). The adapter offers arrays of textures and none of buffers (`BUFFER_ARRAYS` in `crates/runtime/or-renderer/src/game_shaders/meshlets.rs`), so a pass that binds an array of buffers is not one it builds.

**The lighting is not the build's for want of what feeds it.** `openrage-cli rpf scan-rdna-bind <shaders.rpf> <offset> --technique TiledLighting` finds the technique that lights a frame in four effects, and both its stages translate in all four. Its pixel stage reads one binding the view fills, seven or eight samplers, and from 50 to 58 bindings only the game fills; its vertex stage reads four more and the words of a draw. Counted by stage across the four effects that is 64 distinct bindings, each known by the hash of its name and nothing more. What is missing is therefore named, and none of it is translation:

- **What those bindings are.** A program carries no name, so which of the 64 is a list of lights by tile, a shadow map, a probe or a target of the surface pass is not known.
- **The passes that fill them.** By the same count over the large container, the 21 effects whose names say they light, shadow or post-process a frame hold 469 passes of two stages: every one translates and one binds. The compute programs beside them are built by the check and run by nothing.
- **A frame to schedule them in.** The editor's one frame is GTA V's ([what the measures found](../reference/Crate_Reference.md#what-the-measures-found)); a GTA VI model's own passes are a surface pass and one resolve of OpenRage's.
- **The words of a draw**, which the game passes with each draw and the editor has no source for.

## Saves and mission tables

`crates/io/or-io/src/gta6/save.rs` knows three containers. A story save is an index over one JSON text; it opens as an owned value, a value is read or replaced by a path of steps, and it saves. A record is a header before a payload and is read. A packed copy's clear head is read and its body refused.

⚠ **The save reader was written from a description of the layout alone.** No GTA VI save was at hand, so no real save has been opened by it; where its comments say "measured", the measurement is the description's, not OpenRage's. Its tests build their saves by hand from the same description, so they show that the reader and the writer agree with each other and nothing more.

The mission state tables are the opposite case. An inflated body of a script archive is a metadata document in the table form, and a state table is one of its blocks, found by the body's own block table and type table and never by a scan of its bytes (`crates/io/or-io/src/gta6/mission_tables.rs`). They are read only: what orders the states is not proven.

## Text, radio and dialogue

A text table is a map from a label's hash to one text or to the grammatical variants of one. A written table opens as the same table and is not byte-identical to the game's, because the layout the game's writer chose is not known. A table states no language: `crates/io/or-io/src/gta6/text_language.rs` takes it from the order in which a change set registers the text archives, which holds only while the file holds as many as are registered.

Radio and dialogue are joins across bodies, all read only. A station names track lists, a track names a streamed sound by key, and a streamed sound names its audio streams (`crates/io/or-io/src/gta6/audio_radio.rs`). A dialogue line's label is its key in the text tables and its place among a key's labels numbers its audio stream (`crates/io/or-io/src/gta6/dialogue.rs`); the pairs are found by their shape in a body's bytes, not through the body's structure, and a line's number is settled from the streams that exist. `src/state/gta6_dialogue.rs` indexes the open scans so that a line plays with its subtitle in the language picked.

## What was checked against a build

- **Held by a suite.** `crates/io/or-io-verify/tests/ttpf.rs` reads every pack of a GTA VI folder named by `OPENRAGE_GAME_ROOT` and requires each head to hold to the container model and each texture to read or be refused by name. It is install-gated, so a run without the folder is a skip and not a pass.
- **Checked by hand with the CLI.** The other readers were written against the owner's build and re-checked with commands that can fail: `rpf scan-relayout` (the loose-resource writer's rules against stored resources), `rpf scan-particles --validate` (an in-place write gives a section back unchanged), `rpf scan-maps --check` (level-of-detail links resolve), `ttpf plan` (a save's rows against the file's). No suite in the tree runs them, and no measured figure of a build is committed.
- **Tested on inputs built by hand only.** Every unit test under `crates/io/or-io/src/gta6/` and `crates/tools/or-shader-front/src/rdna/` assembles its input from the layout; none reads a game file. Such a test passes when reader and writer are wrong the same way.
- **Not checked against real bytes.** The saves, as above.
- **A patched copy against its source.** The writer compares every table span of a copy with the source's before it returns, and `crates/io/or-io/tests/gta6_patch_in_place.rs` patches rows of each row shape of the build `OPENRAGE_GTA6_BUILD` names, reads each back and counts the rows that fit and those refused by name. It is install-gated, so a run without the build is a skip and not a pass.
- **An edit by each writer, into a patched copy.** `crates/tools/or-cli/tests/gta6_edit_to_patched_copy.rs` edits a real row of each kind with the writer OpenRage edits it with, plans the body into a patched copy and reads the edit back from it; `crates/io/or-io-verify/tests/gta6_edits_that_fit_in_place.rs` deflates sampled chunks of each kind again against their stored sizes; and `a_text_row_of_the_build_saved_from_its_document_reads_back_from_a_patched_copy` opens a text row of the build from the tree in the app's state, saves it into its row and reads it back from a patched copy. Each is install-gated, and the figures are in [GTA_VI_Modding.md](../guides/GTA_VI_Modding.md#what-fits-today).
- **Edits made in the app, each copy against its source.** A text table, a metadata XML and a headerless metadata body of the build were each edited in the app, saved into their row and saved as a patched copy, and each copy was compared with its source outside the app: the same size, the bytes that differ inside the edited row's body, no table span touched, and the inflated body different only in the edited value. It was done by hand, once, on one build, and [GTA_VI_Modding.md](../guides/GTA_VI_Modding.md#how-the-path-was-checked-on-a-build) has the figures; `rpf9 verify-patch` makes the same comparison.
- **Not checked in the game.** Anything written, a patched copy included.
